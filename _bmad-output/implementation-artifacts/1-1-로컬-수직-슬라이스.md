# Story 1.1: 로컬 수직 슬라이스 (스캐폴딩 + 마이그레이션/시드 + 역할 선택)

## Story

As a **서비스를 처음 여는 사용자**,
I want **로컬에서 브라우저 → FastAPI → Supabase가 실제로 관통하는 최소 뼈대에서 역할(환자/직원)을 고를 수 있기를**,
so that **배포(1.2) 전에 전체 3계층이 실제로 도는 것을 눈으로 확인하고, 이후 모든 기능(예약·진료·조회)이 얹힐 땅을 세운다.**

> 이 스토리는 Epic 1의 **뼈대 스토리**다. 넓이(기능)를 늘리는 게 아니라, 나머지 14개 스토리가 전부 딛고 설 **구조·규약·데이터 기반**을 로컬에서 관통시키는 것이 목적이다. 배포(Vercel/Railway)와 배포 환경 RLS 실증은 **Story 1.2**가 맡는다 — 이 스토리는 **로컬 실행까지**다.

## Dev Notes

### 이 스토리의 현재 상태 (greenfield)
- 레포는 **완전 그린필드** — 코드는 `README.md`와 `.gitignore`뿐이고 커밋은 `Initial commit` 하나. `frontend/`·`backend/`·`db/`는 **아직 없다**(이 스토리가 처음 만든다).
- **UPDATE할 기존 파일 없음.** 전부 신규 생성이라 회귀(regression) 위험은 없으나, **한번 세운 구조·규약이 이후 14개 스토리의 표준**이 되므로 아키텍처 스파인 규약을 정확히 따를 것.
- Supabase `fphsxoweprztrekckzui`에 **9테이블은 이미 배포돼 있다**(아래 실측 스키마). **현재 RLS OFF·전 테이블 0행** — 이 스토리가 RLS를 켜고 시드를 넣는다.

### 실측 DB 스키마 (Supabase `fphsxoweprztrekckzui`, live baseline — AD-9)
> **이것이 진실의 원본이다.** `db-design/schema.sql`은 레포에 없다. PK/FK는 전부 `bigint GENERATED ALWAYS AS IDENTITY`. `NN`=NOT NULL, `null`=nullable.

| 테이블 | 컬럼 (타입, 제약) | FK |
|---|---|---|
| `hospital` | id(NN, identity) · name(text NN) · address(text null) · phone(text null) | — |
| `department` | id(NN) · name(text NN, **UNIQUE**) | — (전역 진료과 코드) |
| `hospital_department` | id(NN) · hospital_id(NN) · department_id(NN) | →hospital, →department |
| `doctor` | id(NN) · hospital_department_id(NN) · name(text NN) · license_no(text null) | →hospital_department (현재 소속) |
| `patient` | id(NN) · name(text NN) · birth_date(date null) · gender(text null) · phone(text null) | — |
| `drug` | id(NN) · name(text NN) · unit(text null) | — |
| `appointment` | id(NN) · patient_id(NN) · hospital_department_id(NN) · **doctor_id(null)** · reserved_at(timestamptz NN) · reason(text null) · status(text NN, default `'대기'`, **CHECK ∈ 대기·확정·완료·취소**) | →patient, →hospital_department, →doctor |
| `medical_record` | id(NN) · **appointment_id(null)** · patient_id(NN) · **doctor_id(NN)** · **hospital_department_id(NN)** · visited_at(timestamptz NN) · diagnosis(text null) · notes(text null) | →appointment, →patient, →doctor, →hospital_department |
| `prescription` | id(NN) · medical_record_id(NN) · drug_id(NN) · dosage(text null) · days(int null) | →medical_record, →drug |

**이 스토리에서 반드시 각인할 스키마 함정:**
1. **`appointment.hospital_department_id`는 `hospital_department.id`를 참조**(전역 `department.id` 아님). UI의 "진료과"를 raw `department.id`로 넣으면 **FK 위반**. `GET /departments`가 `hospital_department.id`를 `id`로 돌려주고, 예약도 그 id를 저장한다 (AC5). [Source: review-datamodel.md 매핑 항목]
2. `appointment.doctor_id`는 **nullable**이지만 P0 정책상 예약 생성 시 항상 채운다("DB는 허용, 앱이 강제" 2계층). 이 스토리에선 예약을 만들지 않으니 참고만. [Source: addendum.md#A3]
3. `medical_record.doctor_id`·`hospital_department_id`는 **NOT NULL** — 의사 없이는 기록 생성 불가(후속 스토리). 시드에서 이 테이블은 채우지 않아도 됨.
4. `status` CHECK 값은 **한국어 문자열 그대로**(`대기`·`확정`·`완료`·`취소`). 코드에서 상수로 관리.

### 마이그레이션 SQL (그대로 사용 가능)

`db/migrations/001_rls.sql` — 9테이블 RLS ON, anon 정책 미생성:

### 시드 작성 규칙 (`db/seed/004_seed.sql`)
- PK가 `GENERATED ALWAYS AS IDENTITY`라 **평범한 명시-id INSERT는 에러**. 다음 둘 중 하나:
  - `INSERT INTO ... OVERRIDING SYSTEM VALUE VALUES (고정id, ...)` — FK를 고정 id로 결정적으로 엮을 때
  - `WITH ins AS (INSERT ... RETURNING id) INSERT ... SELECT ... FROM ins` — 상위 행 id를 받아 하위에 넣을 때
- **최소 시드 구성**(시연 충분 최소): 병원 1행 → `department` 여러(예: 내과·이비인후과 등) → 각 department마다 `hospital_department`(병원×진료과) 1행 → **각 hospital_department에 의사 2명 이상**(A4 권장: 자동배정·충돌 시연용) → 약 여러 → 환자 수명(예: 이수민 등, UX 시나리오 이름 활용).
- `medical_record`·`prescription`·`appointment`는 시드하지 않아도 됨(후속 스토리가 UI로 생성). 참조 데이터(병원·진료과·의사·약·환자)만 채우면 이 스토리 목적 충족.

### 마이그레이션/시드 적용 방법
- `db/migrations/`·`db/seed/`의 SQL 파일이 **유일한 스키마 변경 경로**(AD-9, 즉석 DDL 금지).
- 적용은 Supabase MCP(`apply_migration`/`execute_sql`) 또는 Supabase SQL Editor, 또는 `psql "$DATABASE_URL" -f 파일` 중 편한 방법. **순서 001→002→003→004 준수.**
- ⚠️ RLS 활성화는 Supabase advisor가 "critical"로 경고하지만, 여기선 **의도된 결정**(AD-7/NFR-4: anon 차단 + 백엔드 경유). deny-by-default가 목표이므로 그대로 적용한다.

### 백엔드 연결·계층 규약 (AD-1·AD-2)
- **DB 커넥션을 여는 코드는 `app/db/` 계층뿐.** `routers`는 HTTP·검증만, `services`가 비즈니스 규칙·트랜잭션 소유, `db`가 유일한 DB I/O. 상향 import(db→services 등) 금지 [Source: ARCHITECTURE-SPINE.md#AD-2].
- **DATABASE_URL**: Supabase **session-mode 풀러(5432)** 또는 직접 연결 문자열. transaction-mode 풀러(6543)를 쓰면 psycopg 3 자동 prepared statement가 간헐 오류를 내므로 **`prepare_threshold=None`** 설정 필수(안 하면 후속 스토리의 트랜잭션이 배포 환경에서 깨짐) [Source: ARCHITECTURE-SPINE.md 운영 봉투].
- **DATABASE_URL은 env 전용, 프런트 번들 금지**(AD-7, AC8).

### API 계약 (AD-10) — 이 스토리에서 표준을 못 박는다
- 리소스 지향 REST, 라우트는 **복수형**(`/departments`, 이후 `/patients`·`/appointments`·`/medical-records`).
- 성공 = Pydantic 모델 JSON 그대로(커스텀 성공 봉투 없음). 오류 = HTTP status + `{"detail": ...}`(도메인 거부는 4xx + 한국어 메시지).
- 시각은 ISO-8601 UTC(`timestamptz`). id는 전부 정수.
- 연관은 **FK 정수 id + 평평한 표시 필드**(예: `doctor_id` + `doctor_name`), nested/flat 혼용 금지.
- 프런트는 **`lib/api.ts` 단일 클라이언트**만 통해 호출. 화면에서 직접 `fetch` 금지 [Source: EXPERIENCE.md#Foundation].

### 프런트 규약 (AD-1)
- 프런트가 아는 유일한 백엔드 좌표는 `NEXT_PUBLIC_API_BASE_URL`. DB 드라이버·서버 자격증명 import 금지.
- 앱 셸: 상단 **역할 컨텍스트 바** + 콘텐츠(완성은 1.5, 이 스토리는 위치만). 폼은 `max-w-2xl` 단일 컬럼, 직원 목록은 넓은 폭 [Source: DESIGN.md#Layout].
- 문구는 한국어 **해요체**(환자=안심·친근, 직원=간결) [Source: EXPERIENCE.md#Voice-and-Tone].
