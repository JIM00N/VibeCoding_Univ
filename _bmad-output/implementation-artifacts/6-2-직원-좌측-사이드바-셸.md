## Story

As a 접수 직원,
I want 예약관리·신규 환자 등록·환자 목록 검색을 좌측 사이드바에서 바로 오가기를,
so that 자주 쓰는 예약관리를 중심으로 빠르게 이동한다.

**한 줄 성격:** 이 스토리는 **순수 프런트·add-only 레이아웃/내비**다. **신규 마이그레이션·백엔드·API 변경 0**(기존 직원 3화면·API를 그대로 두고 그 위에 셸만 얹는다). 만드는 것은 딱 셋 — ① 직원 좌측 사이드바 컴포넌트(`components/staff-sidebar.tsx` — `usePathname()`로 현재 위치 활성 판정, 모바일 드로어), ② 직원 전용 중첩 레이아웃(`app/staff/layout.tsx` — 모든 `/staff/*`를 사이드바 셸로 감쌈), ③ `/staff` 홈을 `/staff/appointments`로 리다이렉트(예약관리 기본 진입, 사용자 결정 2026-07-26). **기존 홈 카드 3장의 내비 기능은 사이드바로 재배치**될 뿐 사라지지 않는다(회귀 아님). 사이드바는 **`/staff/*`에만** 뜨고, 환자·의사 화면과 **의사가 `?from=doctor`로 쓰는 공유 기록/처방전 폼**에는 뜨지 않는다(직원 화면 전용 셸).

## Acceptance Criteria

**AC1 — 직원 좌측 사이드바: 3 내비 + 활성 표시 (FR-3, UX-DR12)**
**Given** 직원 화면(`/staff/*`)에 진입했을 때
**When** 화면이 렌더된다
**Then** 좌측 사이드바에 **예약관리(강조)·신규 환자 등록·환자 목록·검색** 세 내비 항목이 뜨고, **현재 위치가 활성으로 표시**된다(활성 톤 = Primary Emerald `#047857`, DESIGN.md 크롬 색)
**And** 세 항목은 기존 라우트(`/staff/appointments`·`/staff/patients/new`·`/staff/patients`)와 **동일 대상** — 신규 기능이 아니라 홈 카드 3장의 **재배치**(add-only). 예약관리는 primary 톤으로 강조한다(UX-DR12: "예약관리 강조")

**AC2 — 예약관리 기본 진입 (재배치, 사용자 결정 2026-07-26)**
**Given** 첫 화면에서 `[직원]`을 고르거나 `/staff`로 직접 진입할 때
**When** 화면이 렌더된다
**Then** `/staff`는 `/staff/appointments`로 **리다이렉트**되어 **예약관리가 기본 활성**으로 등장한다(user story "예약관리를 중심으로 빠르게 이동")
**And** 기존 `/staff` 홈 카드 3장(`app/staff/page.tsx`)은 제거되고 그 내비 기능은 **사이드바가 보존**한다(기능 회귀 0 — 위치만 재배치). `[직원]`(`app/page.tsx` → `/staff`)·"직원 홈으로"(`patients/new` → `/staff`) 진입 링크는 이제 예약관리(=새 직원 홈)로 착지한다(정합, 두 페이지 무수정)

**AC3 — 내비 이동 + 컨텍스트 유지**
**Given** 좌측 사이드바에서
**When** 항목을 고른다
**Then** 해당 직원 화면으로 이동하고 사이드바와 상단 역할 컨텍스트 바가 유지된다(각 직원 페이지가 이미 렌더하는 `<RoleContextBar role="직원" />`는 **동결** — 셸은 그 바깥/왼쪽에 얹힐 뿐 페이지 본문을 건드리지 않는다)

**AC4 — 반응형: ≥md 고정 · 모바일 접힘/드로어 (UX-DR12, UX-DR11)**
**Given** 데스크톱과 모바일에서
**When** 화면 폭이 바뀐다
**Then** `≥md`(768px+)는 좌측 사이드바가 **고정**되어 콘텐츠 좌측 rail로 상주하고, 모바일(`<md`)은 **접힘/드로어**(햄버거 토글)로 표시돼 콘텐츠를 가리지 않는다(390×844에서 본문 가독 유지)

**AC5 — 직원 화면 전용 셸: 환자·의사·공유 폼 제외 (UX-DR4, UX-DR12, AD-8 경계)**
**Given** 환자(`/patient/*`)·의사(`/doctor/*`) 화면에서
**When** 본다
**Then** 좌측 사이드바 **없이** 기존 상단 역할 컨텍스트 바만 유지한다(사이드바는 `/staff/*` 라우트 전용 — 환자·의사 라우트는 이 레이아웃 밖이라 자동 제외)
**And** 의사가 `?from=doctor`로 진입하는 **공유 기록/처방전 폼**(`/staff/appointments/[id]/record`·`/staff/appointments/[id]/prescription`, Story 6.1)에는 **사이드바를 렌더하지 않는다** — 이 두 화면은 직원·의사가 공유하며 의사 진입 시 의사 컨텍스트(6.1 `?from=doctor` 역할 바)이므로, 직원 셸을 노출하면 "의사 화면에 사이드바 금지"에 위배된다. 집중 입력/인쇄 폼이라 사이드바 제외가 UX상으로도 맞다

**AC6 — 회귀 0 · 품질 게이트 (add-only P0.5)**
**Given** 이 스토리가 순수 프런트 셸일 때
**When** 구현한다
**Then** **신규 마이그레이션·백엔드·API 변경 0**(라이브 DB·FastAPI 무변경 — 최우선 금기 준수). 기존 직원 페이지 본문·환자·의사 화면·역할 바 **회귀 0**
**And** `npm run lint`·`npm run build` 그린. **브라우저 실측**(390×844 모바일 드로어 + ≥md 고정 rail, 콘솔 0): 3라우트 활성 하이라이트·`/staff`→예약관리 리다이렉트·환자/의사 화면 사이드바 없음·record `?from=doctor` 사이드바 없음 확인

### 🎯 이 스토리의 한 줄 요약

**셸만 얹는다 — 로직·데이터·백엔드 0.** 직원 3화면(`/staff/appointments`·`/staff/patients/new`·`/staff/patients`)은 이미 다 있다. 6.2는 그 위에 ① 좌측 사이드바 컴포넌트, ② 직원 전용 중첩 레이아웃, ③ `/staff`→예약관리 리다이렉트 셋을 add-only로 얹는다. 홈 카드 3장의 내비 기능은 사이드바로 **재배치**될 뿐 사라지지 않는다. **신규 마이그레이션·백엔드·API·도메인 로직 0.**

### 왜 "이미 준비돼 있다" 인가 — 선행 스토리가 남긴 훅

- **1.3~2.2**가 직원 3화면(`/staff/patients/new`·`/staff/patients`·`/staff/appointments`)과 각 화면의 `<RoleContextBar role="직원" />` 상단 바 패턴을 확립했다. → 6.2는 이 라우트를 **내비 대상으로 가리키기만** 하고, 각 페이지 본문·역할 바는 동결.
- **1.5**의 `role-context-bar.tsx`가 상단 역할 컨텍스트 바(UX-DR4)의 정본. 셸은 이 바를 **그대로 두고** 왼쪽에 사이드바 rail만 추가(중복 바 아님 — 상단 바 = 역할/신원, 좌측 rail = 직원 내비).
- **6.1**이 record/prescription을 `?from=doctor`로 **직원·의사 공유 화면**으로 만들었다. → 6.2의 사이드바는 이 공유 폼에서 반드시 **숨겨야** 의사 컨텍스트(AC5)를 안 깬다. 6.1의 `?from=doctor` 역할 바 처리가 이 경계의 근거.
- **6.1**이 `usePathname` 미사용·`useSearchParams`는 Suspense 필요라는 교훈을 남겼다. → 6.2는 활성 판정에 **`usePathname`만** 써 Suspense·프리렌더 이슈를 피한다.

### 설계 결정

1. **`app/staff/layout.tsx` 중첩 레이아웃으로 셸을 add-only 얹기.** Next 16 App Router 중첩 레이아웃은 세그먼트의 모든 자식을 감싼다 → 직원 페이지를 **하나도 수정하지 않고** 모든 `/staff/*`에 사이드바를 붙일 수 있다. 각 페이지는 자기 `<RoleContextBar/>`+`<main>`을 계속 렌더하고, 셸은 그 왼쪽에 rail을 둔다. *(대안: 각 페이지에 사이드바를 개별 삽입 — 6개+ 페이지 수정·회귀 위험, 기각.)*
2. **사이드바는 client 컴포넌트, 활성 판정은 `usePathname()`.** 현재 위치 하이라이트(AC1)에 클라이언트 훅이 필요. `usePathname`은 `useSearchParams`와 달리 **Suspense 경계 불필요** — 셸을 static-친화로 유지(6.1 프리렌더 이슈 회피). 레이아웃 자체는 server 컴포넌트로 두고 client 사이드바만 import.
3. **`/staff` → `/staff/appointments` 리다이렉트(예약관리 기본 진입, 사용자 결정 2026-07-26).** user story "예약관리를 중심으로"·UX-DR12 "예약관리 강조"에 가장 충실. 홈 카드 3장 제거 = **재배치**(내비 기능은 사이드바가 보존, 기능 회귀 0). "직원 홈으로"(`patients/new`) 버튼은 이제 예약관리(=새 홈)에 착지 — 정합이라 그 페이지 무수정. *(대안 B: 홈 카드 유지·셸만 추가 — 사이드바+카드 내비 중복. 대안 C: 홈을 경량 랜딩 — 새 콘텐츠 필요. 둘 다 기각, 사용자 A 선택.)*
4. **공유 record/prescription 폼에서 사이드바 hide(`usePathname` 가드).** 이 두 화면은 직원·의사 공유(6.1 `?from=doctor`)라 의사 진입 시 직원 셸 노출은 AC5("의사 화면에 사이드바 없음") 위배. 사이드바 컴포넌트가 `/(record|prescription)$/`에서 `null` 반환 → 레이아웃 콘텐츠 풀폭 degrade(회귀·print 0). 집중 입력/인쇄 폼이라 사이드바 제외가 UX상으로도 맞다. `?from` 쿼리 대신 **경로**로 판정 — 직원이 그냥 기록 폼을 열어도 focus 유지(단순·정직).
5. **모바일 드로어 = 단순 `useState` 토글 + 오버레이(신규 의존성 0).** shadcn `Sheet`(현재 미설치)·드로어 라이브러리 도입 금지 — 햄버거 + `useState` open + 슬라이드 `<aside>` + 백드롭 ~40줄로 충분. *(더 lazy 대안: `<details>/<summary>` 네이티브 접힘 — client state 0. 폴리시보다 "드로어" AC 문구에 맞춰 useState 채택, dev가 `<details>`를 택해도 무방.)* 활성색은 DESIGN.md **Primary Emerald `#047857`**(크롬/활성 내비 색 — 상태 green과 교차 금지).
