# Story 4.1: 환자 자기 예약·진료 기록 조회

Status: done

> 🚧 **착수 게이트: Story 3.3 done 이후에만 착수한다.** 조회할 데이터(예약·진료 기록·처방)가 Epic 1~3에서 이미 라이브에 존재해야 이 스토리가 성립한다. 3.3 이 만든 정규 응답 모델(`MedicalRecordOut` — 처방 flat 리스트·`prescription_printed_at` 포함)과 2.2 의 예약 목록/배지 패턴을 **그대로 재사용**한다. 이 스토리가 닫히면 **P0 E2E 한 줄기(등록→예약→확정→기록→조회)** 가 배포 URL에서 관통한다(Epic 4 목표).

## Story

As a 환자,
I want 내 예약 목록과 지난 진료 기록(진단·처방)을 보기를,
so that 전화 없이 내 진료 이력을 스스로 확인한다.

**한 줄 성격:** 이 스토리는 **읽기 전용**이다. 신규 마이그레이션 0건, 신규 상태 전이 0건. 백엔드는 이미 반쯤 준비된 두 GET 엔드포인트에 `?patient_id=` 필터를 add-only 로 얹고(2.2 의 `GET /appointments`·3.3 의 `GET /medical-records`), 프런트는 1.5 가 고정해 둔 환자 신원(`patient.id`)을 그 필터 값으로 실사용해 환자용 조회 화면을 연다(AD-8).

## Acceptance Criteria

**AC1 — 내 예약 목록 조회 + 상태 배지 (FR-11, AD-8, UX-DR2)**
**Given** 신원이 선택된 환자(1.5)가
**When** 환자 화면에서 예약을 조회한다
**Then** `GET /appointments?patient_id={patient.id}`(신규 필터)로 **그 환자의 예약만** 상태 배지(`AppointmentStatusBadge` — 대기=amber·확정=blue·완료=green·취소=gray)와 예약 시각(`formatReservedAt`, Asia/Seoul)·진료과·담당 의사와 함께 목록으로 표시된다
**And** 목록 순서는 `reserved_at desc`(최근 예약 먼저), 각 배지는 색만이 아니라 한국어 텍스트를 병기한다(UX-DR9)

**AC2 — 내 지난 진료 기록 조회(진단·소견·발생 진료과·처방 포함) (FR-11, AD-8)**
**Given** 신원이 선택된 환자가
**When** 진료 기록을 조회한다
**Then** `GET /medical-records?patient_id={patient.id}`(신규 대안 필터)로 내 지난 기록이 표시된다 — 각 기록에 진단명(`diagnosis`)·소견(`notes`)·발생 진료과(`department_name`)·담당 의사(`doctor_name`)·진료 일시(`visited_at`)와 **연결된 처방 목록(약 `drug_name`·용법·용량 `dosage`·일수 `days`)** 이 함께 나온다
**And** 응답은 3.3 의 정규 `MedicalRecordOut`(처방을 flat 리스트로 합성, AD-10)을 **그대로** 쓴다 — 새 응답 모델·새 매퍼를 만들지 않는다. 처방전 **출력/인쇄 경로는 만들지 않는다**(처방전은 직원 전용 문서 — epics.md 스코프 경계). 목록 순서는 `visited_at desc`(최근 진료 먼저)

**AC3 — 앱 레벨 필터·데모 고지·환자 전환 (AD-8, UX-DR8)**
**Given** 데모 환경에서
**When** 환자 화면(홈/예약/기록)에 머문다
**Then** "지금은 로그인이 없어 누구나 환자를 고를 수 있어요(데모). 화면을 나눠 보여줄 뿐 진짜 보안 격리는 아니에요." 취지의 **상시 고지 배너**(정보 톤 — `bg-muted/50` Card, ❌ red/destructive 금지)가 유지된다
**And** 상단 역할 컨텍스트 바의 "다른 환자"(→`/patient/select`)로 다른 환자를 고르면 그 환자의 데이터가 보인다 — 이는 앱 레벨 필터일 뿐 기밀 격리가 아니며 UI 문구가 보안을 암시하지 않는다(AD-8)

**AC4 — 빈 상태·오류 분리·반응형(모바일 단일 컬럼) (UX-DR7, UX-DR11, UX-DR10)**
**Given** 예약이나 기록이 없을 때
**When** 조회한다
**Then** 백엔드는 **빈 리스트 `[]`(200, 404 아님 — 목록 계약)** 를 주고, 프런트는 **빈 상태 UI**("아직 예약이 없어요." / "아직 진료 기록이 없어요." 안심 톤)를 보여준다
**And** 렌더 우선순위는 **로딩(Skeleton) > 오류(별도 상태+다시 시도) > 빈 상태 > 목록** — 백엔드 다운(오류)을 "예약 없음"(빈 상태)으로 렌더하지 않는다(1.4/1.5/2.2 리뷰가 반복해 잡은 버그)
**And** 환자 화면은 `max-w-2xl` **단일 컬럼·여유 있는 카드**로 렌더한다(직원용 밀도 표 재사용 금지 — 같은 디자인 언어, 다른 밀도)

**AC5 — 저장된 신원 서버 대조(경량, 신규 백엔드 0) (AD-8, deferred-work 1.5)**
**Given** 환자 홈(`/patient`)에 진입할 때
**When** 저장된 신원(`patient.id`·`patient.name`)이 있다
**Then** 기존 `getPatients()`(1.5 가 쓰는 그 목록 엔드포인트 — **신규 백엔드 없음**)로 서버 목록을 받아 저장된 `id` 를 대조한다: ① 목록이 정상 로드됐는데 그 `id` 가 **없거나**(삭제) ② 찾았는데 **이름이 다르면**(재시드로 id 재할당) `clearPatient()` 후 `/patient/select` 로 보내고 "선택한 환자 정보를 다시 확인해 주세요." 취지 안내를 남긴다 — 이름은 그대로인데 남의 기록을 보는 상황을 막는다
**And** 이름이 일치하면 조용히 통과하고, **목록 호출 자체가 실패(백엔드 다운)하면 신원을 지우지 않는다**(오류≠잘못된 신원 — AC4 오류 분리 원칙과 동일). 대조는 홈 진입 시 1회 — 서브 페이지는 기존 신원 가드에 의존(정상 흐름은 홈 경유)

**AC6 — 백엔드 계약(2엔드포인트 add-only)·회귀 0·품질 게이트 (AD-8, AD-10)**
**Given** 백엔드 두 조회 엔드포인트에 `patient_id` 필터를 얹을 때
**When** 요청이 도달한다
**Then** ① `GET /appointments` — `patient_id` 없으면 **기존 직원 전체 목록 그대로**(회귀 0), 있으면 그 환자로 필터. ② `GET /medical-records` — `appointment_id`(3.3 직원 처방전 경로)와 `patient_id`(신규 환자 조회)를 **둘 다 optional** 로 받아 하나로 분기하며, **둘 다 없으면 400 `{"detail": "조회 조건이 필요해요."}`**(한국어 — 3.3 의 "누락 시 422" 계약을 이 스토리가 소유해 개정, 최소 수정)
**And** `AppointmentOut`/`MedicalRecordOut`/`PrescriptionOut` 정규 모델과 `_to_*_out` 매퍼를 그대로 재사용(리소스당 모델 1개, AD-10), 백엔드 `pytest` 그린(신규 케이스 + 3.3 의 422 테스트를 400 계약으로 개정), 프런트 `npm run lint`·`npm run build` 그린

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

읽기 전용 스토리다. 백엔드는 **이미 반쯤 준비된** 두 GET(`/appointments`·`/medical-records`)에 `?patient_id=` 필터를 add-only 로 얹고(정규 모델·매퍼·처방 jsonb 집계 전부 재사용), 프런트는 1.5 가 고정해 둔 `patient.id` 를 그 필터로 실사용해 환자용 조회 화면 2장(`/patient/appointments`·`/patient/records`)을 연다. **신규 마이그레이션 0·신규 상태 전이 0·신규 응답 모델 0.** 이 스토리가 닫히면 P0 E2E 한 줄기가 배포 URL 에서 관통한다.

### 왜 "반쯤 준비돼 있다" 인가 — 선행 스토리가 남긴 훅

- **1.5** 가 환자 신원을 `localStorage["hospital-care.patient"] = {id, name}` 로 고정하고 `usePatientIdentity()` 훅을 만들었다. 파일 헤더가 명시: *"이 정수 id 가 Epic 4 의 `?patient_id=` 값이 된다."* → 4.1 은 그 id 를 **그대로** 백엔드에 넘긴다.
- **2.2** 의 `GET /appointments` 는 직원 전체 목록이고 docstring 이 *"환자용 조회(?patient_id=)는 Epic 4"* 라 필터를 일부러 안 붙였다. → 4.1 이 그 필터를 얹는다(회귀 없이).
- **3.3** 의 `GET /medical-records?appointment_id=` docstring 이 *"Epic 4 가 나중에 patient_id 대안 필터를 같은 엔드포인트에 얹는다"* 라 남겨뒀다. `MedicalRecordOut` docstring 도 *"Epic 4 의 조회(FR-11 진단·처방 포함)도 이 정규 모델 하나를 그대로 재사용한다"* 라 못 박았다. → 4.1 은 새 모델·새 SQL 형태를 만들지 않는다.

### 설계 결정

1. **라우트 구조 = `/patient` 허브 + 서브 2장.** `/patient` 를 진입 카드 허브로 바꾸고 `/patient/appointments`·`/patient/records` 서브 라우트를 둔다 — 이미 있는 `/patient/book` 서브 라우트 관용을 미러하고, 각 화면을 단일 목적·여유 밀도로 유지한다(환자 톤, UX-DR11). *(대안: `/patient` 한 화면에 두 섹션 인라인. 사용자 확인 질문으로 남김 — 아래 "질문" 절.)*
2. **처방전 출력 경로는 만들지 않는다.** 처방전은 직원 전용 통제 문서(3.3 사용자 결정, epics.md:430). 4.1 은 환자에게 처방 **내역**(무슨 약을 받았는지)만 읽기로 보여준다 — `prescription_printed_at`·`window.print()`·`[처방전 출력]` 버튼 전부 환자 화면에 없음.
3. **정렬:** 예약 `reserved_at desc`, 진료 기록 `visited_at desc`(둘 다 "최근 먼저" — 환자가 최신 이력을 먼저 본다). 직원 목록의 `id desc` 와 다른 이유는 환자 관점의 시간순 가독성.
4. **`GET /medical-records` 계약 개정.** `appointment_id` 를 optional 로 완화하고 `patient_id` 대안을 추가. "둘 다 없음"은 **400 한국어**(3.3 의 422 는 필수 쿼리 부작용이었을 뿐, AD-10 도메인 거부는 4xx+한국어가 정본). 실제 프런트는 항상 한쪽을 보내므로 이 400 은 방어선이다. 3.3 직원 처방전 경로(`?appointment_id=`)는 그대로 동작(회귀 0).

### SQL 청사진 — 읽기 2종 (add-only, `%s` 파라미터만)

**① `_SELECT_APPOINTMENTS_BY_PATIENT`** (`db/appointments.py` — 기존 `_SELECT_APPOINTMENTS` 표시 조인 미러):

```sql
select a.id, a.patient_id, a.hospital_department_id, a.doctor_id, a.reserved_at, a.status,
       p.name   as patient_name,
       doc.name as doctor_name,
       d.name   as department_name
from public.appointment a
join public.patient p               on p.id  = a.patient_id
join public.hospital_department hd  on hd.id = a.hospital_department_id
join public.department d            on d.id  = hd.department_id
left join public.doctor doc         on doc.id = a.doctor_id
where a.patient_id = %s
order by a.reserved_at desc
```

**② `_SELECT_RECORDS_BY_PATIENT`** (`db/medical_records.py` — 3.3 `_SELECT_RECORDS_BY_APPOINTMENT` 를 `where`·`order by` 만 바꿔 미러. 처방 jsonb 집계 그대로 — Python N+1 재조립 금지):

```sql
select mr.id, mr.appointment_id, mr.patient_id, mr.hospital_department_id,
       mr.doctor_id, mr.visited_at, mr.diagnosis, mr.notes,
       mr.prescription_printed_at,
       p.name   as patient_name,
       doc.name as doctor_name,
       d.name   as department_name,
       coalesce(
           (select jsonb_agg(jsonb_build_object(
                'id', pr.id, 'drug_id', pr.drug_id, 'drug_name', dr.name,
                'dosage', pr.dosage, 'days', pr.days) order by pr.id)
            from public.prescription pr
            join public.drug dr on dr.id = pr.drug_id
            where pr.medical_record_id = mr.id),
           '[]'::jsonb) as prescriptions
from public.medical_record mr
join public.patient p               on p.id  = mr.patient_id
join public.hospital_department hd  on hd.id = mr.hospital_department_id
join public.department d            on d.id  = hd.department_id
join public.doctor doc              on doc.id = mr.doctor_id
where mr.patient_id = %s
order by mr.visited_at desc
```

> ⚠️ **표시 조인 SQL 사본 규약(deferred).** 위 두 SELECT 는 기존 표시 조인의 N번째 사본이 된다 — 이는 2.1·2.2·3.3 이 정한 **의도적 컨벤션**이다. 공유 fragment 로 뽑는 리팩터는 별도 정리 스토리 몫(deferred-work). 4.1 은 관용을 **따르기만** 하고 리팩터하지 않는다.
> `medical_record` 의 `doctor` 는 INNER JOIN(doctor_id NOT NULL), `appointment` 의 `doctor` 는 LEFT JOIN(doctor_id nullable) — 스키마 차이를 그대로 미러(정직).

### 저장된 신원 vs 서버 대조 (사용자 결정 2026-07-25 — 경량 처리 포함, AC5)

deferred-work(1.5 리뷰)는 *"저장된 신원을 서버와 대조하지 않음 … 재시드·환자 삭제로 `id=1` 이 다른 사람에게 재할당되면 이름은 그대로·데이터는 남의 것 … Epic 4 의 실데이터 조회에서 근본 처리"* 라며 4.1 을 처리 지점으로 지목했다. **사용자 결정:** 이번 스토리에서 경량으로 처리한다(AC5·Task 4).

**구현 방침 — 신규 백엔드 0.** `GET /patients/{id}` 를 새로 만드는 대신 **1.5 가 이미 쓰는 `getPatients()` 목록을 재사용**한다:
- 이 방식이 더 가볍고(백엔드 3계층 동결 유지) **오류와 오판을 깔끔히 분리**한다 — 목록이 **정상 200 으로 로드됐는데** 저장된 `id` 가 없으면 "확실히 삭제됨"이고, 목록 호출 자체가 throw 하면 "백엔드 다운"이라 신원을 건드리지 않는다. `GET /patients/{id}` 는 `request` 헬퍼가 상태코드를 버려(Error 메시지만) 404 와 네트워크 오류를 구분하기 어렵다 — 목록 재사용이 그 함정을 피한다.
- 홈(`/patient`) 진입 1회 대조로 충분(정상 흐름은 홈 경유). 서브 페이지 직접 URL 진입까지 막지는 않는다(무인증 데모의 기존 한계 — AD-8, 새 구멍 아님). 완전한 per-request 격리는 여전히 실인증(Deferred, AD-7)의 몫.
