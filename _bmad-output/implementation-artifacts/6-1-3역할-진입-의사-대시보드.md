## Story

As a 의사,
I want 첫 화면에서 `[의사]` 역할을 고르고 내 신원을 선택해 나에게 배정된 예약을 먼저 보기를,
so that 직원 화면을 거치지 않고 내 진료 대상만 바로 확인하고 진료 기록을 남긴다.

**한 줄 성격:** 이 스토리는 **프런트 중심·add-only** 다. **신규 마이그레이션 0**(데이터 모델은 이미 `doctor_id`+`status` 를 지님), **신규 백엔드는 `GET /appointments?doctor_id=` 필터 1개뿐**(Story 4.1 이 얹은 `?patient_id=` 필터의 **의사판** — 라우터·서비스·db·SQL 미러, 신규 스키마 0). 만드는 프런트는 ① 첫 화면에 `[의사]` 버튼, ② 의사 신원 스토어(`lib/doctor-identity.ts` — `patient-identity.ts` 미러), ③ 의사 신원 선택 화면(`/doctor/select` — `patient/select` 미러), ④ 의사 대시보드(`/doctor` — `patient/page.tsx` 가드 + `staff/appointments/page.tsx` 렌더 미러, 활성/완료 분류), ⑤ 역할 바(`role-context-bar.tsx`)에 `"의사"` 확장이다. **진료 기록 작성은 Story 3.1 의 `/staff/appointments/[id]/record` 를 그대로 재사용**한다(신규 폼·로직 0). **의사 스코핑은 `?doctor_id=` 앱 레벨 필터일 뿐 보안 격리가 아니다**(AD-8, 데모 고지 유지).

## Acceptance Criteria

**AC1 — 3역할 진입 (FR-1)**
**Given** 첫 화면(`/`)에서
**When** 역할 버튼을 본다
**Then** `[환자]`·`[직원]`·`[의사]` **세** 역할 버튼이 뜨고, `[의사]` 클릭 시 `/doctor` 로 이동한다
**And** 기존 `[환자]`(→`/patient`)·`[직원]`(→`/staff`) 동작과 수직 슬라이스 관통 카드(`GET /departments` 렌더, AC6 of 1.1)는 **동결**(회귀 0). 버튼 그리드만 3열로 확장(add-only)

**AC2 — 의사 신원 선택 + `?doctor_id=` 스코핑 (FR-1b, AD-8, UX-DR8)**
**Given** `[의사]` 를 선택했을 때
**When** 의사 목록(전체 의사 `GET /doctors`, 진료과 무관)에서 본인을 고른다
**Then** 그 의사 신원이 컨텍스트로 고정되고, 이후 의사 화면은 `GET /appointments?doctor_id=` 로 **그 의사에게 배정된 예약만** 필터한다(앱 레벨 필터, 보안 아님)
**And** "로그인 대체·기밀 격리가 아니며 누구나 임의 의사를 고를 수 있음(데모)" 고지 배너를 신원 선택 화면과 대시보드에 유지한다(UX-DR8, AD-8 — 환자 화면 고지 문안·배치 미러)

**AC3 — 역할 컨텍스트 바(의사) 유지 (UX-DR4)**
**Given** 의사 신원이 선택된 상태에서
**When** 화면을 이동하거나 새로고침한다
**Then** 상단 역할 컨텍스트 바가 현재 역할(**의사**) + 선택 의사명(`○○○ 선생님`) + 전환 액션(다른 의사 → `/doctor/select`, 역할 바꾸기 → `/`)을 유지해 보여준다
**And** 신원은 `localStorage` 에 영속되어 새로고침·재진입에도 유지된다(`patient-identity.ts` 의 `useSyncExternalStore`·메모리 폴백·도메인 검증 패턴 미러)

**AC4 — 의사 대시보드: 활성 우선 + 완료 분류 (FR-17, UX-DR2)**
**Given** 의사 대시보드(`/doctor`)에서
**When** 배정 예약을 조회한다
**Then** **활성 예약(status ∈ 대기·확정)** 이 상태 배지와 함께 **먼저** 표시되고, **완료 전이된 예약(status = 완료)** 은 활성 목록에서 빠져 **"완료된 진료"** 로 분류돼 표시된다(클라이언트 `status` 분류 — **신규 스키마·신규 서버 필터 없음**)
**And** 취소된 예약(status = 취소)은 의사 worklist 노이즈라 두 섹션 모두에서 제외한다(전이 소유는 직원 화면 — 2.2). 각 섹션 빈 상태 안내("배정된 활성 예약이 없어요." / "완료된 진료가 없어요.")

**AC5 — 확정 예약에서 진료 기록 작성 재사용 → 완료 전이 → 활성에서 사라짐 (FR-17, AD-5)**
**Given** 대시보드의 **확정** 상태 배정 예약에서
**When** 의사가 진료 기록을 작성한다
**Then** **Story 3.1 의 폼·계약(`/staff/appointments/[id]/record`)을 그대로 재사용**해 기록이 생성되고 같은 트랜잭션에서 그 예약이 확정→완료로 전이된다(**신규 로직·신규 폼 0**)
**And** 완료된 예약은 대시보드 **활성 목록에서 사라지고 "완료된 진료"로 분류**된다(재조회 시 반영). 대기 예약에는 기록 작성 진입점을 노출하지 않는다(확정 예약에만 작성 가능 — 3.1 서비스 가드가 최종 관문)

**AC6 — 반응형 밀도 (UX-DR11)**
**Given** 데스크톱과 모바일에서
**When** 화면 폭이 바뀐다
**Then** `≥md` 는 밀도 있는 표, 모바일은 카드로 접혀 표시된다(`staff/appointments/page.tsx` 표/카드 렌더 미러 — 단 **담당 의사 열 제거**(항상 본인)·**쓰기 액션은 [기록 작성]만**)

**AC7 — 경계·회귀 0·품질 게이트 (AD-8, AD-9, AD-10)**
**Given** 이 스토리가 add-only P0.5 일 때
**When** 구현한다
**Then** **신규 마이그레이션 0**(라이브 DB 무변경 — 최우선 금기 준수). 백엔드는 `GET /appointments?doctor_id=` 필터만 add-only(라우터 파라미터·서비스 분기·db 함수·SQL 사본 1개 — 4.1 `?patient_id=` 미러). 기존 화면(환자·직원)·기존 API 메서드 **회귀 0**
**And** 백엔드 `pytest -q` 그린(신규 `?doctor_id=` 계약 테스트 추가 — 4.1 `test_list_appointments_by_patient_*` 미러), 프런트 `npm run lint`·`npm run build` 그린(신규 라우트 `/doctor`·`/doctor/select` 등록). 의사 스코핑은 **앱 레벨 필터·보안 아님**을 UI 고지로 유지(AD-8)

### 설계 결정

1. **의사 스코핑 = `?doctor_id=` 앱 레벨 필터(AD-8 의사판).** 환자 스코핑(`?patient_id=`)과 동일 성격 — 보안 격리가 아니라 데모 필터다. 신규 스키마·서버측 status 필터 없음. 활성/완료 **분류는 클라이언트**가 `status` 로 나눈다(FR-17: "status 필터 — 신규 스키마 없음").
2. **의사 신원 스토어는 환자와 별도 파일(`doctor-identity.ts`).** 한 스토어에 두 역할을 섞지 않는다 — `patient-identity.ts` 주석 정신(역할 개념 격리) 계승. `STORAGE_KEY` 는 `hospital-care.doctor`(환자 키와 분리 — 역할 전환 시 서로 안 침범).
3. **역할 바는 add-only 확장(리팩터 아님).** `role` 유니온에 `"의사"` 추가 + `doctorName`/`doctorAction` prop 을 환자 props **옆에** 얹는다(기존 `patientName`/`patientAction` 동결). "이름 표시 ↔ 액션 분리" 원칙 계승. prop-driven 유지(바가 스토어를 직접 읽지 않음).
4. **`getDoctors(hdId)` 는 동결, 전체 조회는 신규 `getAllDoctors()`.** 백엔드 `/doctors` 는 이미 무필터=전체지만, 프런트는 2.1·2.3 이 의존하는 `getDoctors(hospitalDepartmentId: number)` 시그니처를 **바꾸지 않는다**(add-only규율). *(대안: 파라미터 optional 화 — 하위호환이나 동결 규율상 신규 메서드가 안전.)*
5. **진료 기록 작성 = 3.1 라우트 재사용 + `?from=doctor` 역할-인지(신규 폼·도메인 로직 0, 채택안 B — 사용자 결정 2026-07-26).** epics.md AC "Story 3.1 의 폼·계약을 그대로 재사용, 로직 신규 없음" 이행. as-is 재사용 시 record 페이지 역할 바가 `"직원"` 으로 뜨고 저장 후 직원 화면에 착지하는 leak 을 피하려, `?from=doctor` 쿼리 분기만 add-only 로 얹어 역할 바·복귀 경로를 의사판으로 돌린다(Task 8). *(대안 A: 그대로 재사용·record 무변경 — P0.5 수용 가능했으나 UX-DR4 역할 연속성 위해 B 채택.)*
6. **취소 예약은 대시보드에서 제외.** FR-17 은 활성(대기·확정)·완료만 언급. 취소는 의사 worklist 노이즈이고 전이 소유는 직원(2.2)이라 두 섹션 모두에서 뺀다(정직: 의사는 취소를 관리하지 않음).
7. **대시보드 액션은 [기록 작성](확정)만.** 확정/취소/의사 변경은 직원이 소유(AD-5·2.2·2.3) — 의사 화면에 전이 버튼을 두지 않는다(중복 진입점 방지, 읽기+기록작성 경계).

### 핵심 안티패턴 (하지 말 것)

- **신규 마이그레이션·스키마 변경 금지.** `doctor_id`+`status` 로 충분(FR-17). 라이브 공용 DB 변경은 최우선 금기.
- **패턴이 아니라 이유를 복제.** `patient-identity.ts` 의 `useSyncExternalStore`·메모리 폴백·`ready` 규약은 이 레포에서 다른 방식이 깨지기 때문에 존재한다 — **이유째로** 복제(주석 계승). "왜 lazy useState 가 아닌가/왜 effect 내 동기 setState 가 아닌가"를 지운 채 복사하지 말 것.
- **표시 조인 SQL 을 지금 공유 fragment 로 추출하지 말 것.** 6번째 사본이 되더라도 기존 5사본의 의도적 컨벤션을 따른다(일괄 정리는 별도 스토리 — deferred-work 2.3).
- **역할 바를 리팩터하지 말 것.** `patientName`/`patientAction` 을 일반화(`identityName` 등)하려는 유혹 금지 — 동작 중인 환자/직원 사용처 회귀 위험. add-only 확장만.
- **대시보드에 상태 전이·처방전 출력 버튼을 넣지 말 것.** 확정/취소/재배정=2.2·2.3, 처방전 출력=3.3 소유. 의사 화면은 조회+[기록 작성]만.
