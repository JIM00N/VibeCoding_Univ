# Story 4.2: 직원 환자별 전체 진료 내역 조회

Status: review

> 🚧 **착수 게이트: Story 4.1 done 이후에만 착수한다.** 4.1 이 백엔드 두 GET 에 `?patient_id=` 필터를 이미 얹었고(`getAppointmentsByPatient`·`getMedicalRecordsByPatient`) 환자용 조회 화면 2장을 열었다. 4.2 는 **같은 두 필터를 직원 관점(특정 환자 특정 후 전체 내역)으로 재사용**한다. 이 스토리가 닫히면 **Epic 4 가 완료**되고 **P0 E2E 한 줄기(등록→예약→확정→기록→조회)가 환자·직원 양쪽에서 배포 URL 로 관통**한다 → Epic 6(3역할, correct-course) 착수 게이트가 열린다(실행 순서 Epic 4 → Epic 6 → Epic 5).

## Story

As a 접수 직원,
I want 특정 환자의 예약·진료·처방 전체 내역을 한 화면에서 보기를,
so that 그 환자의 상태를 파악해 응대한다.

**한 줄 성격:** 이 스토리는 **프런트 전용·읽기 전용**이다. **신규 백엔드 0**(4.1 이 만든 두 `?patient_id=` GET 을 그대로 호출), **신규 마이그레이션 0**, **신규 API 메서드·타입 0**, **쓰기 액션 0**. 만드는 것은 프런트 화면 하나 — 환자 목록(1.4)에서 환자를 클릭하면 진입하는 상세 라우트 `/staff/patients/[id]` — 와 목록 행을 그 상세로 잇는 링크뿐이다. 예약은 직원 밀도(≥md 표·모바일 카드, `/staff/appointments` 렌더 미러하되 **액션 제거**), 진료 기록은 카드(처방 중첩, 4.1 `/patient/records` 렌더 미러)로 한 화면에 얹는다.

## Acceptance Criteria

**AC1 — 진입: 환자 목록 행 → 상세 (FR-12)**
**Given** 직원이 환자 목록(`/staff/patients`, Story 1.4)에서
**When** 환자 행(≥md 표) 또는 모바일 카드를 클릭한다
**Then** 그 환자의 상세 화면 `/staff/patients/{id}` 로 이동한다 — `staff/patients/page.tsx:5` 가 남긴 훅 *"행 클릭 상세 이동은 Story 4.2 범위라 여기선 표시만"* 을 이행한다
**And** 목록 페이지에는 **상세 링크만 add-only** 로 얹고, 검색·디바운스(250ms)·빈/오류 분리·`genderText`/`orDash` 표시 로직은 **동결**(회귀 0)

**AC2 — 한 화면에 예약·진료 기록·처방 (FR-12)**
**Given** 직원이 특정 환자 상세(`/staff/patients/{id}`)에 진입했을 때
**When** 데이터가 로드된다
**Then** 상단에 **환자 식별 헤더**(이름 + 생년월일·성별·연락처 — 누구의 내역인지 확정), 그 아래 **예약 섹션**(그 환자의 예약 목록)과 **진료 기록 섹션**(진단·소견·발생 진료과·담당 의사·진료 일시 + **연결된 처방 목록** nested)이 한 화면에 표시된다
**And** 세 데이터(`getPatients()`·`getAppointmentsByPatient(id)`·`getMedicalRecordsByPatient(id)`)를 **`Promise.all` 병렬 로드**한다(3.3 처방전 페이지 패턴 미러 — 어느 하나라도 throw 하면 화면 전체 ErrorState)
**And** 처방은 각 진료 기록 카드 **안에** 중첩 표시한다(별도 flat "처방" 섹션을 만들지 않는다 — 처방은 `medical_record` 의 자식이라 nested 가 정본, AD-10 `prescriptions` 배열 그대로)

**AC3 — 정규 모델·기존 API 메서드 그대로 재사용 (AD-10)**
**Given** 내역을 조회할 때
**When** 데이터가 온다
**Then** 응답은 리소스별 정규 모델(`Appointment`·`MedicalRecord`·`Prescription` — FK 정수 id + 평평한 표시 필드)로 일관되게 오고, 프런트는 4.1 이 만든 `api.getAppointmentsByPatient`·`api.getMedicalRecordsByPatient` 를 **그대로** 호출한다
**And** **신규 API 메서드·신규 타입·신규 백엔드 엔드포인트를 만들지 않는다**(`lib/api.ts`·`schemas`·`routers`·`services`·`db` 무변경). 환자 식별 헤더의 인적사항도 **기존 `getPatients()` 재사용**(4.1 AC5 가 정한 "환자를 id 로 해소할 땐 목록 재사용, 신규 백엔드 0" 방침 — `GET /patients/{id}` 신설 금지)

**AC4 — 반응형 밀도·로딩·오류·빈 상태 (UX-DR11, UX-DR7, UX-DR10)**
**Given** 데스크톱과 모바일에서
**When** 화면 폭이 바뀐다
**Then** **예약 섹션**은 `≥md` 밀도 표·모바일 카드(`/staff/appointments` 표/카드 렌더 미러 — 단 **읽기 전용**: 액션 열·버튼 없음, 환자 이름 열 제거(이미 특정 환자)), **진료 기록 섹션**은 카드(처방 중첩, `/patient/records` 렌더 미러 — **인쇄/출력 machinery 전부 제외**)로 표시된다
**And** 로딩 중에는 Skeleton, 조회 실패는 **ErrorState**(다시 시도 + "환자 목록으로"), 예약/기록이 각각 없으면 **섹션별 빈 상태**("아직 예약이 없어요." / "아직 진료 기록이 없어요." 직원 톤=간결)
**And** 렌더 우선순위 **로딩 > 오류 > (섹션별)빈 상태 > 목록** — 백엔드 다운(오류)을 "내역 없음"(빈 상태)으로 렌더하지 않는다(1.4/1.5/2.2/4.1 이 반복해 잡은 버그). 직원 화면은 `max-w-4xl` 밀도 레이아웃(환자용 `max-w-2xl` 단일 컬럼과 구분 — 같은 디자인 언어, 다른 밀도)

**AC5 — 환자 부재·오류 분리·잘못된 id 방어 (AD-8, 4.1 AC5 규율 재적용)**
**Given** 없는 환자 id(삭제·잘못된 URL) 또는 백엔드 다운 상태에서 상세에 진입할 때
**When** 로드한다
**Then** `getPatients()` 목록이 **정상 200 으로 로드됐는데** 그 `id` 가 목록에 **없으면** "환자를 찾을 수 없어요." 안내 + "환자 목록으로"(→`/staff/patients`)를 보여준다(확실히 삭제/오타). 반대로 로드 자체가 **throw(백엔드 다운)면 ErrorState**(다시 시도) — 오류≠부재(4.1 AC5 와 동일 원칙, "백엔드 다운을 환자 삭제로 오판 금지")
**And** URL 세그먼트 `id` 가 **정수>0 이 아니면**(예: `/staff/patients/abc`) 로드하지 않고 방어한다(`validId` — 3.3 처방전 페이지 `Number.isInteger && > 0` 패턴 미러)

**AC6 — 읽기 전용 경계·회귀 0·품질 게이트 (AD-8, AD-10)**
**Given** 이 스토리가 조회 전용일 때
**When** 구현한다
**Then** **쓰기 액션 0** — 예약 확정/취소/의사 변경은 `/staff/appointments`(2.2·2.3)가 소유하고, 처방전 출력/인쇄는 `/staff/appointments/[id]/prescription`(3.3)이 소유한다. 이 조회 화면에는 그 어떤 전이 버튼·`window.print()`·`[처방전 출력]`·`prescription_printed_at` 표시도 **없다**(내역 열람 전용)
**And** 백엔드 무변경(신규 파일·엔드포인트·마이그레이션 0), 기존 목록 페이지 검색·`getPatients` 회귀 0, 프런트 `npm run lint`·`npm run build` 그린(신규 라우트 `/staff/patients/[id]` 등록). 백엔드 `pytest` 는 무변경이나 회귀 없음 재확인용 그린

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

**프런트 전용·읽기 전용** 스토리다. 백엔드는 4.1 이 이미 두 GET 에 `?patient_id=` 필터를 얹어 뒀다 — 4.2 는 그 두 메서드(`getAppointmentsByPatient`·`getMedicalRecordsByPatient`)를 **직원 관점**으로 재호출하고, 환자 인적사항은 기존 `getPatients()` 로 해소한다. 만드는 것은 화면 하나(`/staff/patients/[id]`)와 목록→상세 링크뿐. **신규 백엔드 0·신규 마이그레이션 0·신규 API 메서드 0·신규 타입 0·쓰기 액션 0.** 이 스토리가 닫히면 **Epic 4 완료 = P0 E2E 한 줄기가 환자·직원 양쪽에서 배포 URL 로 관통**한다.

### 왜 "이미 다 준비돼 있다" 인가 — 선행 스토리가 남긴 훅

- **4.1** 이 `GET /appointments?patient_id=`·`GET /medical-records?patient_id=` 필터와 `api.getAppointmentsByPatient`·`api.getMedicalRecordsByPatient`(배열 방어 포함)를 만들었다. → 4.2 는 **그대로 호출**(새 메서드·새 SQL 없음). `MedicalRecord` 타입에 `prescriptions: Prescription[]` nested 도 이미 있다.
- **1.4** 의 `staff/patients/page.tsx:5` 가 못 박음: *"행 클릭 상세 이동은 Story 4.2 범위라 여기선 표시만."* → 4.2 가 그 링크를 얹는다(검색·표/카드 로직 동결).
- **3.3** 의 `prescription/page.tsx` 가 **동적 라우트 `[id]` 클라이언트 페이지 + `useParams` + `Promise.all` 병렬 로드 + `validId` 방어**의 정본 패턴을 남겼다. → 4.2 상세 페이지는 이 구조를 그대로 미러(async `params` prop 아님).
- **4.1** 의 `patient/records/page.tsx` 가 **기록+처방 카드 렌더**(처방 중첩·인쇄 없음)의 정본을, `staff/appointments/page.tsx` 가 **직원 밀도 표/카드**의 정본을 남겼다. → 4.2 는 이 둘을 조합(예약=표/카드, 기록=카드).

### 설계 결정

1. **라우트 = `/staff/patients/[id]` 동적 상세.** 기존 `/staff/appointments/[id]/record`·`/prescription` 동적 라우트 관용을 미러한다(직원 리소스 상세는 `[id]`). 목록(`/staff/patients`)이 부모, 상세가 자식. *(대안: 목록 행 인라인 확장 — 밀도·딥링크·새로고침에 불리해 기각.)*
2. **환자 인적사항도 `getPatients()` 재사용(신규 백엔드 0).** 4.1 AC5 가 정한 방침 — "환자를 id 로 해소할 땐 목록을 재사용, `GET /patients/{id}` 신설 금지". 이점: ① 백엔드 3계층 완전 동결, ② **오류(백엔드 다운) vs 부재(삭제/오타)를 깔끔히 분리**(목록 200 로드 후 id 부재 = 확실히 없음; throw = 백엔드 다운이라 부재로 오판 안 함). `request` 헬퍼가 상태코드를 버려 `GET /patients/{id}` 는 404 와 네트워크 오류를 못 가른다 — 목록 재사용이 그 함정을 피한다.
3. **레이아웃 = 예약 표 + 기록 카드(사용자 결정 2026-07-26).** 예약은 tabular 하니 `/staff/appointments` 밀도 표/카드를 미러(읽기 전용·환자 열 제거). 진료 기록은 처방이 N:1 자식이라 표 셀에 안 맞음 → 4.1 records 카드(처방 중첩)를 미러. UX-DR11 "밀도 표" 요건은 **예약 섹션**이 충족하고, 기록은 "같은 디자인 언어, 다른 밀도"의 카드다(정직).
4. **읽기 전용 경계.** 4.2 는 **뷰어**다. 상태 전이·재배정은 `/staff/appointments`, 처방전 출력은 `/staff/appointments/[id]/prescription` 이 소유(중복 진입점 안 만듦). 이 화면에 [처방전] 점프오프를 넣고 싶은 유혹이 있으나 — 스코프(epics.md 4.2 = 조회)·읽기 전용 명료성·중복 방지를 위해 **넣지 않는다**(원하면 예약관리 완료행에서, 3.3). Deferred 로도 올리지 않음(의도적 경계).
5. **환자 헤더의 `RoleContextBar` 는 `role="직원"` 만.** 직원 화면엔 "선택 환자" 신원 개념이 없다(`patientName` prop 은 환자 화면 전용 — role-context-bar.tsx 주석). 보고 있는 환자 이름은 **페이지 헤더**가 표시한다(역할 바 아님).

### 핵심 안티패턴 (하지 말 것)

- ❌ **신규 백엔드/엔드포인트/마이그레이션/API 메서드/타입 발명** — 전부 4.1·1.4 가 만든 것 재사용. 이 스토리는 백엔드 파일을 **하나도** 안 만진다.
- ❌ **`GET /patients/{id}` 신설** — `getPatients()` 재사용(4.1 AC5 방침, 오류/부재 분리). 
- ❌ **쓰기 액션·전이 버튼·처방전 출력·`window.print()`·`prescription_printed_at` 표시** — 조회 전용(AC6). 전이는 `/staff/appointments`, 출력은 3.3 이 소유.
- ❌ **오류를 빈 상태로, 오류를 "환자 부재"로 렌더** — 목록이 **정상 200** 일 때만 id 부재를 "환자 없음"으로 판정. throw 는 ErrorState(1.4→1.5→2.2→4.1 반복 버그).
