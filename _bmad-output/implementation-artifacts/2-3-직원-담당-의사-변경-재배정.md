# Story 2.3: 직원 담당 의사 변경 (재배정)

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 접수 직원,
I want 예약의 담당 의사를 다른 의사로 바꾸기를,
so that 사정에 맞춰 진료 의사를 조정한다.

## Acceptance Criteria

**AC1 — 담당 의사 변경: `doctor_id`만 갱신, 정규 모델 응답 (FR-7 P0, AD-10, AD-2)**
**Given** 대기 또는 확정 상태의 예약이 있을 때
**When** 직원이 같은 진료과의 다른 의사를 선택해 변경한다
**Then** `PATCH /appointments/{id}/doctor`(body `{"doctor_id": <int>}`)로 `appointment.doctor_id`**만** 갱신되고 — `status`·`reserved_at`·`hospital_department_id`는 불변 — 응답이 리소스 정규 모델 `AppointmentOut`(정수 FK id + 평평한 표시 필드, **갱신된 `doctor_id`와 `doctor_name` 포함**)으로 온다
**And** 변경 로직은 **서비스(`services/appointments`)만** 소유한다(AD-2) — 라우터는 HTTP 입출력, db는 SQL I/O만

**AC2 — 의사 변경 UI: 현재 담당 의사 + 같은 진료과 후보 (UX-DR9)**
**Given** 직원 예약 관리 화면(`/staff/appointments`)의 대기·확정 예약 행에서
**When** `[의사 변경]` 액션을 누른다
**Then** **1단계 Dialog**(비파괴적 — destructive 스타일 금지)에 **현재 담당 의사**와 **같은 진료과의 선택 가능한 의사 목록**(`GET /doctors?hospital_department_id=` 재사용)이 보인다
**And** 현재 담당 의사는 후보에서 제외(또는 비활성)되어 "**다른** 의사" 선택만 가능하고, 바꿀 다른 의사가 없으면 안내 문구와 함께 확인 버튼이 비활성된다
**And** Select에 라벨이 있고 키보드로 조작 가능하며 `Esc`로 닫힌다(UX-DR9). 완료·취소 예약 행에는 `[의사 변경]` 액션이 노출되지 않는다

**AC3 — 도메인 가드: 서비스가 4xx 한국어로 거부 (AD-10, AD-5 보존)**
**Given** 부적격 요청일 때
**When** 서버에 도달한다
**Then** 서비스가 다음을 순서대로 가드하고 `{"detail":"…한국어 문자열…"}`로 거부한다:
- 없는 예약 → **404** · 완료/취소 상태 예약 → **400**(대기·확정만 변경 가능)
- 없는 의사 → **400** · **다른 진료과 의사 → 400**(같은 진료과 의사만) · 현재 담당 의사와 같은 의사 → **400**
- UPDATE는 **compare-and-set**(`where id=%s and status = any(%s)`)으로 수행, 0행이면 **409**(2.2 리뷰 patch 패턴 미러) — 동시 상태 변경과의 경쟁에서 취소/완료 예약 재배정이 성립하지 않는다
**And** 어떤 경로에서도 `status`는 변경되지 않는다(AD-5 — status 전이 코드는 이 스토리에 없음)

**AC4 — 표시 일관·회귀 0: 행 교체로 의사 배지 자동 갱신 (UX-DR7, 2.4 정합)**
**Given** 변경에 성공했을 때
**When** 저장이 끝난다
**Then** 성공 toast를 띄우고 **PATCH 응답 행으로 그 항목만 교체**한다 — 2.4의 의사 색 배지가 새 `doctor_id` 기반 결정적 매핑으로 **이름과 색이 함께** 자동 갱신된다(별도 색 코드 수정 없음)
**And** 확정/취소 액션·상태 배지·진료과 배지·예약 시각·표(≥md)/카드(<md) 반응형은 그대로 동작한다(2.2·2.4 회귀 0). 실패 시 toast.error + `reloadNonce` 재동기화(2.2 patch 패턴)
**And** 백엔드 `pytest` 그린(기존 테스트 회귀 0) + 프런트 `npm run lint`·`npm run build` 그린

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

2.2가 세운 예약 관리 화면과 PATCH 3계층 패턴 위에, **`PATCH /appointments/{id}/doctor` 엔드포인트 하나**와 **의사 변경 Dialog 하나**를 add-only로 얹는다. 같은 진료과 검증·의사 존재 검증은 **2.1이 만든 `fetch_doctor_department`와 400 문구를 그대로 재사용**하고, 성공 응답 행 교체만으로 2.4 색 배지가 자동 정합된다. **가용성 재검사는 절대 만들지 않는다**(Epic 5).

### ⚠️ 스코프 경계 — 이 스토리의 심장 (무엇을 만들고, 무엇을 만들지 않나)

**IN(만든다):**
- `PATCH /appointments/{id}/doctor` — `doctor_id`만 갱신. 대기·확정 예약 한정. 같은 진료과 검증.
- 예약 관리 화면의 `[의사 변경]` 행 액션 + 비파괴적 Dialog(현재 의사 + 같은 과 후보 Select).
- `components/ui/dialog.tsx`(base-ui dialog 합성) + `lib/api.ts` `updateAppointmentDoctor`.

**OUT(만들지 않는다):**
- **가용성 재검사 = Epic 5(Story 5.1).** `check_and_occupy`·`exclude_appointment_id`·슬롯 해제/점유·`taken` 셀·(의사,슬롯) 충돌 판정을 **부르지도 만들지도 말 것**. 스파인 AD-4가 "P1의 전체 재검사 플로우는 Deferred"로 명시. P0 의사 변경엔 슬롯 충돌 오류 경로 자체가 없다.

- **진료과 변경 없음.** `hospital_department_id`는 불변 — 다른 과 의사로의 이동은 이 스토리도 이후 스토리도 아닌 스코프 밖. 후보는 항상 그 예약의 진료과 안에서만.
- **환자 화면 노출 없음.** 직원 예약 관리 화면 전용. 환자 예약 조회는 Epic 4.
- **새 색맵·새 배지·refdata 변경 없음.** 2.4 `category-color.ts`·`category-badge.tsx`, `refdata` 3계층은 그대로 재사용(수정 금지).

### 엔드포인트 결정 — 왜 `PATCH /appointments/{id}/doctor`인가

기존 `PATCH /appointments/{id}`는 `AppointmentStatusUpdate.status`가 **필수**(누락 시 422 — 2.2 테스트가 이 계약을 고정: `test_patch_missing_status_returns_422`). 여기에 `doctor_id`를 섞으려면 status를 optional로 완화해야 해서 **2.2 계약·테스트가 깨진다.** 서브리소스 `PATCH /appointments/{appointment_id}/doctor`(body `{"doctor_id": int}`)는:
- add-only(기존 라우트·스키마·테스트 무수정), 리소스 지향 REST 유지(AD-10 위반 없음 — 스파인은 verb/경로 세부를 지정하지 않음),
- 응답은 동일한 `AppointmentOut` 정규 모델(AD-10 "리소스당 응답 모델 1개" 충족),
- status 소유권(AD-5)과 doctor 변경을 코드 경로 수준에서 분리해 실수 여지를 없앤다.

### 백엔드 청사진 — SQL·가드 체인

> `appointment` 실측 컬럼(2.1·2.2 실증): `id`(bigint IDENTITY PK)·`patient_id`·`hospital_department_id`·`doctor_id`(**nullable**, 앱이 P0에서 채움 강제)·`reserved_at`(timestamptz)·`status`(text CHECK ∈ 대기·확정·완료·취소). `doctor` 컬럼: `id`·`hospital_department_id`·`name`·`license_no`(시드 `db/seed/004_seed.sql` 실증).

**`_UPDATE_APPOINTMENT_DOCTOR` (compare-and-set CTE, `_UPDATE_APPOINTMENT_STATUS` 미러):**
```sql
with updated as (
    update public.appointment
    set doctor_id = %s
    where id = %s and status = any(%s)
    returning id, patient_id, hospital_department_id, doctor_id, reserved_at, status
)
select a.id, a.patient_id, a.hospital_department_id, a.doctor_id, a.reserved_at, a.status,
       p.name as patient_name, doc.name as doctor_name, d.name as department_name
from updated a
join public.patient p               on p.id  = a.patient_id
join public.hospital_department hd  on hd.id = a.hospital_department_id
join public.department d            on d.id  = hd.department_id
left join public.doctor doc         on doc.id = a.doctor_id
```
0행 = 그 사이 status가 대기·확정 밖으로 바뀜 → 서비스가 409(2.2 문구 재사용).
placeholder 순서 주의 — 함수 시그니처는 `update_appointment_doctor(appointment_id, doctor_id, allowed_sources)`지만 execute는 SQL 순서대로: `cur.execute(_UPDATE_APPOINTMENT_DOCTOR, (doctor_id, appointment_id, list(allowed_sources)))`(미러 원본 `update_appointment_status`와 동일 방식).

**`set_appointment_doctor` 가드 체인(순서 고정 — `set_appointment_status` 미러):**
1. `fetch_appointment(appointment_id)` → None → **404** "예약을 찾을 수 없어요." (2.2 재사용)
2. `current["status"] not in _DOCTOR_CHANGE_SOURCE("대기","확정")` → **400** — 완료: "완료된 예약은 담당 의사를 바꿀 수 없어요." / 취소: "취소된 예약은 담당 의사를 바꿀 수 없어요."
3. `fetch_doctor_department(payload.doctor_id)` → None → **400** "담당 의사를 찾을 수 없어요. 다시 선택해 주세요." (2.1 재사용)
4. `!= current["hospital_department_id"]` → **400** "선택한 진료과의 담당 의사가 아니에요. 의사를 다시 선택해 주세요." (2.1 재사용)
5. `payload.doctor_id == current["doctor_id"]` → **400** "이미 담당하고 있는 의사예요. 다른 의사를 선택해 주세요." (신규 문구 — 해요체·실행 가능)
6. `update_appointment_doctor(...)` → None → **409** (2.2의 CAS 문구 그대로)
7. `_to_appointment_out(row)` 반환.

**GOTCHA(반드시 처리):**
- `AppointmentDoctorUpdate.doctor_id`는 `int` 필수 — 누락은 Pydantic 422(2.2의 status 누락 422와 동일 계약). 값 검증(존재·같은 과)은 서비스 400 — **Literal/제약을 Pydantic에 넣지 말 것**(422 리스트 detail → 일반 메시지 붕괴, 2.1·2.2 확립 패턴).
- 도메인 거부는 전부 `HTTPException(4xx, detail="한국어 str")` — `lib/api.ts`가 문자열 detail만 그대로 보여준다.
- `fetch_appointment`(검증)과 UPDATE가 별도 커넥션이므로 **CAS의 `status = any(%s)`가 최종 안전망**이다(2.2 리뷰 patch #1과 동일한 이유). 검증만 믿고 CAS를 빼지 말 것.
- 현재 `doctor_id`가 null인 예약(이론상 — P0 앱은 항상 채움)이라도 가드 ⑤는 `None == new_id`가 성립하지 않아 자연 통과 — 별도 분기 불필요.

### 프런트 화면 설계 (의사 변경 플로우 — AC2, AC4)

- **행 액션(상태 분기 확장):** `대기` → `[확정]`(primary)+`[취소]`(destructive/outline)+`[의사 변경]`(outline) / `확정` → `[취소]`+`[의사 변경]` / `완료`·`취소` → 없음. 표(≥md)·카드(<md) 동일 렌더(`renderActions` 한 곳 수정).
- **Dialog(비파괴적, 1단계):** UX 스파인은 의사 변경 UI 형태를 못박지 않고 "행 액션: 확정·취소·의사 변경"만 명시(EXPERIENCE.md IA). 파괴적이 아니므로 **`alert-dialog`가 아닌 일반 `dialog`**(Esc 닫힘, 확인 버튼 primary emerald — destructive red 금지). 모달 1단계만(Dialog 위에 Dialog 금지).
