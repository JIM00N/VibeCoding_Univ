# Story 2.2: 직원 예약 확정·취소 & 상태 흐름

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 접수 직원,
I want 들어온 예약을 확정하거나 취소하고 상태를 한눈에 보기를,
so that 예약 흐름을 관리한다.

## Acceptance Criteria

**AC1 — 예약 확정: 대기→확정 전이, 배지 갱신 (FR-7, FR-8, AD-5, AD-10)**
**Given** 대기 상태의 예약이 있을 때
**When** 직원이 예약 관리 화면에서 그 예약을 확정한다
**Then** `PATCH /appointments/{id}`(body `{"status":"확정"}`)로 status가 **대기→확정**으로 전이되고, 응답이 리소스 정규 모델(정수 FK id + 평평한 표시 필드, AD-10)로 오며, 그 행의 상태 배지가 즉시 **확정(blue)** 으로 갱신된다
**And** status 전이는 **예약 서비스만** 소유한다(AD-5) — 라우터/db 가 직접 status 를 바꾸지 않는다
**And** 확정은 **대기 상태에서만** 가능하다 — 확정/완료/취소 예약을 확정 시도하면 `4xx {"detail":"…한국어…"}`(문자열)로 막는다

**AC2 — 예약 취소: 확인 Dialog 1단계 → 취소 전이 (FR-7, FR-8, UX-DR6, AD-4 P0 경계)**
**Given** 대기 또는 확정 상태의 예약이 있을 때
**When** 직원이 취소를 누른다
**Then** 파괴적 액션이라 **shadcn(base-ui) 확인 Dialog 1단계**("정말 취소할까요?" + 되돌릴 수 없음 명시 + destructive 확인)를 거친 뒤에만 `PATCH /appointments/{id}`(body `{"status":"취소"}`)로 status가 **→취소**로 전이되고 그 행의 배지가 **취소(gray)** 로 갱신된다
**And** 이미 취소/완료된 예약은 취소할 수 없다 — 서비스가 `4xx {"detail":"…한국어…"}` 로 막는다
**And** 취소는 그 슬롯을 향후 충돌 대상에서 제외한다 — **P0에서는 status='취소'로 두는 것만으로 충족**된다(Epic 5의 충돌 쿼리가 취소를 제외한다). **`check_and_occupy`·점유 해제 로직을 2.2에서 만들지 않는다**(§스코프 경계)

> 📎 **AC2 완료 판정(스코프 경계):** "슬롯 해제"는 별도 점유 테이블/해제 코드가 아니라 **status='취소' 전이 자체**로 충족한다. 가용성 엔진(`check_and_occupy`, `taken` 셀)은 **Epic 5(Story 5.1)** 다. 2.2에서 그 함수를 **부르지도 만들지도 말 것**.

**AC3 — 상태 배지: 4값 전 화면 동일 매핑, 색+텍스트 병기 (UX-DR2, UX-DR9)**
**Given** 예약 목록에서
**When** 각 예약의 상태 배지가 표시된다
**Then** **대기=amber·확정=blue·완료=green·취소=gray** 로 전 화면 동일 매핑되고(2.1의 `AppointmentStatusBadge` 재사용), 색만이 아니라 **한국어 텍스트를 항상 병기**한다(색맹·SR 접근성)
**And** 2.1이 대기만 노출했던 배지 컴포넌트를 이 스토리가 **확정/취소(+완료 표시)까지** 실사용한다 — 새 배지 매핑을 다시 만들지 않는다

**AC4 — 반응형: 데스크톱 표 · 모바일 카드 (UX-DR11)**
**Given** 데스크톱과 모바일에서
**When** 화면 폭이 바뀐다
**Then** **≥md 는 밀도 있는 표**(환자·진료과·담당 의사·예약 시각·상태·액션), **모바일(<md)은 카드**로 접혀 표시된다 — Story 1.4(`app/staff/patients/page.tsx`)의 표/카드 반응형 패턴을 그대로 미러한다
**And** 로딩 중 Skeleton, 예약 0건 빈 상태, 조회 실패 오류 상태(빈 상태와 구분)를 1.4 패턴대로 처리한다

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

2.1이 만든 `appointments` 3계층에 **`GET /appointments`(직원 전체 목록) 하나**와 **`PATCH /appointments/{id}`(status 전이) 하나**를 더하고, `patients` 목록 화면(1.4)을 복제한 **직원 예약 관리 화면**에서 **확정(대기→확정)** 과 **취소(→취소, 확인 Dialog 경유)** 를 친다. 상태 배지(2.1 컴포넌트)를 4값 전부 실사용하고, 가용성/점유는 **건드리지 않는다**(Epic 5).

**OUT(만들지 않는다):**

- **진료 기록 작성 링크/진입 = Epic 3.** 예약 관리 화면에서 "진료 기록 작성"(확정 예약 행)은 3.1 범위. 2.2는 확정/취소만.

### 백엔드 청사진 — SQL·전이 규칙 (2.1 실측 스키마 기반)

> ⚠️ `appointment` 컬럼(2.1에서 실증): `id`(bigint IDENTITY, PK), `patient_id`, `hospital_department_id`, `doctor_id`(nullable), `reserved_at`(timestamptz), `status`(text, CHECK ∈ 대기·확정·완료·취소, 기본 `대기`). enum 값은 **한국어 문자열 그대로**(스파인 Consistency).

**`GET /appointments` SELECT(직원 전체, 표시 필드 조인):**
```sql
select a.id, a.patient_id, a.hospital_department_id, a.doctor_id, a.reserved_at, a.status,
       p.name   as patient_name,
       doc.name as doctor_name,
       d.name   as department_name
from public.appointment a
join public.patient p               on p.id  = a.patient_id
join public.hospital_department hd  on hd.id = a.hospital_department_id
join public.department d            on d.id  = hd.department_id
left join public.doctor doc         on doc.id = a.doctor_id
order by a.id desc
```
`doctor`는 `LEFT JOIN`(스키마 nullable 정직, 2.1과 동일). 정렬은 `a.id desc`(방금 들어온 예약이 위) — 사소한 UX 선택이라 `reserved_at` 정렬로 바꿔도 무방하나 **일관되게 하나만**.

**`PATCH` UPDATE(status 전이, 한 왕복 CTE — 표시 필드 조인):**
```sql
with updated as (
    update public.appointment
    set status = %s
    where id = %s
    returning id, patient_id, hospital_department_id, doctor_id, reserved_at, status
)
select a.id, a.patient_id, a.hospital_department_id, a.doctor_id, a.reserved_at, a.status,
       p.name as patient_name, doc.name as doctor_name, d.name as department_name
from updated a
join public.patient p               on p.id  = a.patient_id
join public.hospital_department hd  on hd.id = a.hospital_department_id
join public.department d            on d.id  = hd.department_id
left join public.doctor doc         on doc.id = a.doctor_id
```
전이 적격성은 **서비스가 먼저 검증**(아래) — UPDATE 는 검증 통과 후에만 실행. 없는 id 는 `fetch_appointment`가 먼저 404 를 낸다.

**status 전이 매트릭스 (AD-5 — 예약 서비스만 소유):**

| 현재 \ 목표 | 확정 | 취소 |
| --- | --- | --- |
| 대기 | ✅ | ✅ |
| 확정 | ❌ 이미 확정 | ✅ |
| 완료 | ❌ 이미 완료 | ❌ 완료라 취소 불가 |
| 취소 | ❌ 취소된 예약 | ❌ 이미 취소 |

- 목표값 `완료`·기타 = **항상 거부**(400 "확정 또는 취소만 가능해요."). 완료는 Epic 3의 tx 부작용.
- 되돌리기(확정→대기, 취소→대기) 없음.

**GOTCHA(반드시 처리):**
- **도메인 거부는 `HTTPException(400, detail="한국어 str")`, 없는 리소스는 404.** `detail`이 문자열이라야 `lib/api.ts`가 그대로 보여준다(422 리스트/객체 금지). `AppointmentStatusUpdate.status`를 Pydantic `Literal`로 두면 잘못된 값이 422→일반 메시지가 되므로 **`str`로 받고 서비스가 400**으로 막는다(2.1의 `doctor_id`·1.3의 gender 패턴 동일).
- **status 전이는 서비스만.** 라우터는 HTTP·입출력만, `db`는 SQL I/O만(AD-2). 전이 규칙을 라우터/db에 흘리지 말 것.
- **RLS 9테이블 ON.** 백엔드는 `DATABASE_URL`(테이블 소유자)로 RLS 우회, 풀(`db/pool.py`) 경유 서버측. 브라우저 anon 은 아무것도 못 함.
