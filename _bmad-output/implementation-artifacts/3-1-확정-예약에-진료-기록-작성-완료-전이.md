# Story 3.1: 확정 예약에 진료 기록 작성 & 완료 전이

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 의사(직원 화면에서 진료),
I want 확정된 예약에 진단·소견·진료일시를 기록하기를,
so that 진료 내용이 남고 그 예약이 완료 처리된다.

## Acceptance Criteria

**AC1 — 기록 생성 + 같은 트랜잭션 완료 전이 (FR-9, FR-8, AD-5, AD-2)**
**Given** 확정 상태의 예약이 있을 때
**When** 의사가 진단명·소견·진료일시를 입력해 저장한다
**Then** `POST /medical-records`(body `{"appointment_id", "diagnosis", "notes?", "visited_at"}`)로 기록이 생성되고(201, `MedicalRecordOut` 정규 모델), **같은 트랜잭션에서** 그 예약이 확정→완료로 전이된다
**And** INSERT+UPDATE는 **db 계층의 단일 함수가 한 커넥션·한 트랜잭션(단일 CTE 문)**으로 수행한다(Epic 2 회고 액션 #4) — 서비스가 두 db 호출로 쪼개지 않는다
**And** 라우터는 HTTP 입출력만, 가드 체인은 서비스만, SQL은 db 계층만 소유한다(AD-2)

**AC2 — 도메인 가드: 확정 예약에만 작성, 4xx 한국어 거부 (AD-5, AD-10)**
**Given** 부적격 요청일 때
**When** 서버에 도달한다
**Then** 서비스가 다음을 가드하고 `{"detail":"…한국어 문자열…"}`로 거부한다:
- 진단명 빈 값 → **400** · 없는 예약 → **404**(2.2 문구 재사용)
- 대기/취소/완료 상태 예약 → **400**(상태별 문구 — 확정 예약에만 작성 가능)
- `doctor_id`가 null인 예약 → **400**(FR-9 — 작성 시점에 담당 의사 지정 필요)
- CAS 0행(검사 후 상태가 바뀐 경쟁) → **409**(2.2 문구 재사용) — 거부 경로에서 db 쓰기 함수는 호출되지 않는다

**AC3 — AD-6 스냅샷 복사: 과·의사·환자를 작성 시점 값으로 자체 저장**
**Given** 진료 기록을 생성할 때
**When** 저장한다
**Then** `patient_id`·`hospital_department_id`·`doctor_id`는 **그 예약 행에서 SQL이 직접 복사**한다(`insert … select from appointment`) — 클라이언트가 보낸 값을 신뢰하지 않고, 라이브 조인으로 유도하지도 않는다(이력 불변)
**And** 요청 스키마는 `extra="forbid"`로 세 컬럼의 클라이언트 주입을 422 거부한다

**AC4 — 예약당 기록 1건: 부분 유니크가 막고 전이도 롤백 (AD-9, FR-8)**
**Given** 이미 진료 기록이 있는 예약일 때
**When** 두 번째 기록 작성을 시도한다
**Then** 부분 유니크 인덱스 `uq_medical_record_appointment`의 `UniqueViolation`을 서비스가 잡아 **409** 한국어로 거부하고, 단일 문장 원자성으로 **완료 전이도 함께 롤백**된다(기록 없이 완료되는 예약이 생기지 않음)

**AC5 — UI: 확정 행 진입 → 기록 페이지 → 완료(green) 배지 (UX-DR7, UX-DR2, UX-DR9)**
**Given** 직원 예약 관리 화면(`/staff/appointments`)의 **확정** 예약 행에서
**When** `[기록 작성]` 액션으로 진료 기록 페이지에 진입해 저장한다
**Then** 대상 예약 카드(환자·예약 시각·진료과·담당 의사·확정→완료 배지 미리보기)와 라벨된 폼(진단명 필수·소견·진료 일시 읽기전용)이 보이고, 저장 성공 시 toast를 띄우고 예약 목록으로 복귀하며 해당 예약 배지가 **완료(green)**로 표시된다
**And** 확정이 아닌 예약으로 URL 직접 진입하면 폼 대신 안내를 보여준다(작성 불가). 진단명 빈 제출은 라벨 연결된 인라인 오류로 막는다(UX-DR9)
**And** 대기/완료/취소 행에는 `[기록 작성]`이 노출되지 않고, 기존 확정/취소/의사 변경 액션·표/카드 반응형은 그대로 동작한다(2.2·2.3·2.4 회귀 0). 백엔드 `pytest` 그린 + 프런트 `npm run lint`·`npm run build` 그린

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

2.1~2.3이 확립한 3계층 미러를 **새 리소스 `medical_records`**로 복제하되, 이 프로젝트 **첫 다중 문장 트랜잭션**을 "단일 CTE 문 하나 = db 함수 하나"로 해결한다(회고 액션 #4). UPDATE(확정→완료 CAS)와 INSERT(예약 행에서 스냅샷 복사)가 한 문장이라 원자성이 공짜고, `UniqueViolation`이면 전이까지 같이 롤백된다. 프런트는 확정 행 → 기록 페이지(목업 `record.html`) → 저장 → 목록 복귀. **처방(0..N 행)은 3.2 — 이 스토리에서 만들지 않는다.**

### 트랜잭션 설계 — 회고 액션 #4 (이 스토리의 심장)

현재 db 계층은 함수마다 `with get_pool().connection()`으로 자기 커넥션을 연다(커넥션 context 종료 시 commit, 예외 시 rollback — psycopg_pool 기본). INSERT+UPDATE를 서비스에서 두 db 호출로 쪼개면 **커넥션이 달라 원자성이 깨진다.** 해법은 아키텍처 리팩터가 아니라 **db 함수 하나가 단일 CTE 문으로 두 쓰기를 실행**하는 것:

```sql
-- db/medical_records.py · _INSERT_RECORD_AND_COMPLETE
with completed as (
    update public.appointment
    set status = '완료'
    where id = %s
      and status = '확정'          -- CAS: 검사 후 상태가 바뀐 경쟁의 최종 안전망
    returning id, patient_id, hospital_department_id, doctor_id
),
inserted as (
    insert into public.medical_record
        (appointment_id, patient_id, hospital_department_id, doctor_id,
         visited_at, diagnosis, notes)
    select c.id, c.patient_id, c.hospital_department_id, c.doctor_id,
           %s, %s, %s
    from completed c               -- AD-6: 예약 행에서 그 순간 값 복사(클라이언트 미신뢰)
    returning id, appointment_id, patient_id, hospital_department_id,
              doctor_id, visited_at, diagnosis, notes
)
select i.id, i.appointment_id, i.patient_id, i.hospital_department_id,
       i.doctor_id, i.visited_at, i.diagnosis, i.notes,
       p.name   as patient_name,
       doc.name as doctor_name,
       d.name   as department_name
from inserted i
join public.patient p              on p.id  = i.patient_id
join public.hospital_department hd on hd.id = i.hospital_department_id
join public.department d           on d.id  = hd.department_id
join public.doctor doc             on doc.id = i.doctor_id
```

- **왜 단일 문장인가:** PostgreSQL은 한 문장을 원자적으로 실행한다. CAS 0행이면 `completed`가 비어 INSERT도 0행 → `fetchone()` None(아무것도 안 씀). `UniqueViolation`이면 문장 전체가 실패 → **완료 전이도 자동 롤백**(AC4). 별도 `conn.transaction()` 블록 불필요.
- placeholder 순서(2.3 gotcha 재현 주의): 함수 시그니처는 `insert_medical_record_and_complete(appointment_id, visited_at, diagnosis, notes)`, execute는 SQL 순서 그대로 `(appointment_id, visited_at, diagnosis, notes)` — 이번엔 일치하지만 확인하고 쓸 것.
- 표시 조인까지 한 왕복 — `_UPDATE_APPOINTMENT_STATUS`(db/appointments.py:77-94)의 CAS CTE+조인 패턴을 리소스만 바꿔 미러. doctor 조인은 **inner**(medical_record.doctor_id NOT NULL — appointments의 left와 다름).
- **AD-5 소유권 해석(중요):** appointments 서비스의 `_CLIENT_SETTABLE_STATUS`가 완료를 의도적으로 제외한 이유가 바로 이 스토리다 — **확정→완료 전이는 records의 tx 부작용으로만 존재**한다(스파인 AD-5 원문 + Capability Map "services/records(완료 전이 동일 tx)"). `set_appointment_status`를 호출하거나 완료를 화이트리스트에 추가하지 말 것.

   - 완료: "이미 진료가 완료된 예약이에요."
   - else: "이 예약에는 진료 기록을 작성할 수 없어요."
4. `current["doctor_id"] is None` → **400** "담당 의사가 지정되지 않은 예약이에요. 담당 의사를 먼저 지정해 주세요." (FR-9 — DB `doctor_id NOT NULL` 삽입 오류가 500으로 새기 전에 앱이 먼저 거부. P0 앱은 항상 채우므로 이론상 경로지만 가드는 한 줄)
5. `try: insert_medical_record_and_complete(…) except UniqueViolation:` → **409** "이미 진료 기록이 있는 예약이에요." (`from psycopg.errors import UniqueViolation` — create_appointment의 `ForeignKeyViolation` catch 스타일 미러, services/appointments.py:67-73)
6. 반환 None(CAS 경쟁) → **409** "예약 상태가 방금 바뀌었어요. 목록을 새로고침한 뒤 다시 확인해 주세요." (2.2 문구 그대로)
7. `_to_medical_record_out(row)` 반환.

**GOTCHA:** 필수 누락·타입 오류는 Pydantic 422(list detail → 프런트가 일반 메시지로 마스킹 — 확립 패턴이므로 정상). 도메인 규칙은 전부 서비스 4xx 한국어 문자열. **Pydantic에 min_length·Literal 넣지 말 것**(2.1·2.2 확립).

### 실측 스키마 (2026-07-24 라이브 Supabase introspection — 이것이 진실)

```text
medical_record: id bigint PK · appointment_id bigint NULL (FK→appointment ON DELETE SET NULL)
              · patient_id bigint NOT NULL (FK→patient CASCADE)
              · doctor_id bigint NOT NULL (FK→doctor RESTRICT)
              · hospital_department_id bigint NOT NULL (FK→hospital_department RESTRICT)
              · visited_at timestamptz NOT NULL
              · diagnosis text NULL · notes text NULL
부분 유니크: uq_medical_record_appointment on (appointment_id) where appointment_id is not null
```

- **스냅샷 복사 대상은 3개다** — 문서(AD-6)는 과·의사 2개만 말하지만 실측상 `patient_id`도 NOT NULL이라 함께 예약 행에서 복사한다(위 CTE가 이미 처리).
- `diagnosis`·`notes`는 **DB nullable** — "진단명 필수"는 앱 레벨 규칙(가드 ①)이다. DB CHECK에 기대지 말 것.
- `visited_at`엔 30분 CHECK **없음**(그건 `reserved_at` 전용). 임의 시각 저장 가능 — 정렬·검증 불필요.
- `appointment_id`는 nullable(walk-in용, 5.3)이지만 **이 스토리에선 항상 채워진다**(CTE가 예약 행에서만 INSERT).
- 참조: drug 테이블에 시드 4행 실재(3.2용 — 이 스토리 무관).

### 핵심 안티패턴 (하지 말 것)

- ❌ **INSERT와 UPDATE를 서비스에서 두 db 호출로 쪼개기** — 커넥션이 달라 원자성 파괴. 단일 CTE 문 하나(회고 액션 #4). db 함수 안에서 두 `execute`로 나누는 것도 금지(한 문장이 더 단순하고 UniqueViolation 롤백이 공짜).
- ❌ **스냅샷 3필드를 클라이언트 요청에서 받기 / Python에서 fetch한 값을 INSERT 파라미터로 전달** — SQL이 예약 행에서 직접 복사(`insert … select`). fetch(가드용)와 INSERT 사이의 의사 변경 경쟁까지 차단된다.
- ❌ **`set_appointment_status` 호출 또는 `_CLIENT_SETTABLE_STATUS`에 "완료" 추가** — 완료 전이는 records tx의 부작용뿐(AD-5). 2.2 계약·테스트 파괴 금지.
- ❌ **기록 존재 pre-check SELECT 추가** — 부분 유니크 인덱스가 원천 차단(AC4). `UniqueViolation` catch 409로 충분. 검사 쿼리를 늘리지 말 것.
- ❌ **처방 필드·행 UI·`GET /drugs` 선제작** — 3.2 스코프. "미리 만들어두기" 금지.
- ❌ **`GET /medical-records` 목록 선제작** — Epic 4 스코프.
- ❌ **Pydantic에 min_length·Literal·상태 검증** — 422 list detail은 프런트에서 일반 메시지로 붕괴. 도메인 규칙은 서비스 4xx 한국어(확립 패턴).
- ❌ **`visited_at`에 30분 정렬 검증** — 그 CHECK는 `reserved_at` 전용. 진료 일시는 임의 시각.
- ❌ **낙관적 UI / 저장 후 페이지에 머물며 상태 수동 갱신** — 비관적 저장 + 목록 복귀(목록 재조회가 완료 배지의 진실).
- ❌ **SQL 문자열 조립**(f-string/`+`) — `%s` 파라미터만.
- ❌ **하드닝 파일 수정** — `config.py`·`db/pool.py`·`lib/api.ts`의 `request`·`refdata` 3계층·`appointment-status.ts`·`appointment-status-badge.tsx`·`category-color.ts`·`category-badge.tsx`·`role-context-bar.tsx`·`format.ts`·`db/migrations/*`·`db/seed/*`(재실행 금지). `main.py`는 **마운트 2줄만** 예외.
- ❌ **기존 appointments 테스트 수정** — add-only(GET 단건 2건만 추가). 2.2·2.3 계약 테스트는 한 글자도 안 바뀌고 통과해야 한다.
