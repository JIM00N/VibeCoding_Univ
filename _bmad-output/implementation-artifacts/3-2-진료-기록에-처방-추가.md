# Story 3.2: 진료 기록에 처방 추가 (0..N)

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 의사(직원 화면에서 진료),
I want 진료 기록에 처방(약·용법·용량·처방일수)을 0개 이상 추가하기를,
so that 환자에게 필요한 약을 기록으로 남긴다.

## Acceptance Criteria

**AC1 — 처방 행 0..N 반복·추가/삭제 UI (FR-10, UX-DR5, UX-DR9)**
**Given** 진료 기록 폼(`/staff/appointments/[id]/record`, 3.1이 만든 페이지)에서
**When** 약을 고르고 용법·용량·처방일수를 입력해 행을 추가한다
**Then** 처방 행이 0..N개로 반복되며 `+ 처방 추가`로 행을 추가하고 각 행의 `✕`로 삭제할 수 있다
**And** 약 드롭다운은 `GET /drugs`(refdata add-only 신규)가 준 시드 약 목록으로 채워진다
**And** 행이 0개면 빈 상태 문구를 보여주고, 각 입력은 라벨 연결(sr-only 가능)·키보드 조작 가능하다(UX-DR9)

**AC2 — 저장 시 각 처방이 기록에 N:1로 연결, 전부 한 문장 원자성 (FR-10, AD-2, AD-5·AD-6 연장)**
**Given** 처방 행들을 입력했을 때
**When** 기록을 저장한다
**Then** `POST /medical-records` body 의 `prescriptions` 배열(각 항목 `{drug_id, dosage?, days?}`)로 각 처방이 그 `medical_record`에 N:1로 생성된다
**And** 기록 INSERT + 확정→완료 전이 + 처방 INSERT 는 **3.1의 단일 CTE 문을 확장한 한 문장**으로 실행된다(all-or-nothing) — 서비스가 처방을 별도 db 호출로 쪼개지 않는다
**And** 존재하지 않는 `drug_id`면 `ForeignKeyViolation`을 서비스가 잡아 **400** 한국어로 거부하고, 문장 전체가 롤백된다(기록·완료 전이·다른 처방 전부 없던 일 — 처방만 빠진 기록이 생기지 않음)
**And** 응답 `MedicalRecordOut`(정규 모델)에 `prescriptions`가 실린다 — 각 항목은 flat(`id`·`drug_id`·`drug_name`·`dosage`·`days`), nested drug 객체 금지(AD-10)

**AC3 — 처방 0개 허용 (FR-10)**
**Given** 처방 행이 하나도 없을 때
**When** 저장한다
**Then** 처방 없이도 기록이 저장된다(`prescriptions` 생략·`[]` 모두 허용, 3.1 동작 그대로) — 응답 `prescriptions: []`

**AC4 — 미완성 행 차단: 인라인이 먼저, 서버가 최종 관문 (UX-DR9, AD-10)**
**Given** 약을 선택하지 않은 처방 행이 있을 때
**When** 저장한다
**Then** 그 행의 약 필드에 라벨 연결된 인라인 오류로 저장을 막는다(서버 미도달)
**And** 일수를 입력했는데 1 이상의 정수가 아니면 그 행의 일수 필드 인라인 오류로 막는다
**And** 서버도 최종 관문: 행에 `drug_id` 누락·잘못된 타입·스냅샷류 여분 필드 주입은 **422**(`extra="forbid"`), `days < 1`은 **400** 한국어(서비스 가드), db 쓰기 미호출

**AC5 — 회귀 0 + 품질 게이트**
**Given** 3.1이 배포한 기록 작성 흐름에서
**When** 이 스토리를 얹는다
**Then** 3.1의 가드 체인(빈 진단명 400·404·상태별 400·doctor null 400·중복 409·CAS 409)·완료 전이·성공 toast·목록 복귀·완료(green) 배지가 그대로 동작한다
**And** 백엔드 `pytest` 그린 — **기존 테스트 수정은 medical-records 계약 변경이 강제하는 최소 6곳뿐**(Task 3 과 "Testing / 검증 기준" 절에 위치까지 명시), patients·appointments·slots·error_handler 테스트는 한 글자도 안 바뀌고 통과. 프런트 `npm run lint`·`npm run build` 그린

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

3.1의 단일 CTE 문에 **`rx`(처방 INSERT) CTE 하나를 더 얹어** 기록+완료 전이+처방 0..N 을 여전히 **한 문장**으로 쓴다 — 신규 백엔드 모듈 0개, 새 마이그레이션 0개(prescription·drug 테이블 기배포·RLS ON). 프런트는 3.1 이 자리를 예약해 둔 기록 페이지에 목업 `record.html`의 처방 행 리피터를 얹고, 약 목록은 refdata 에 `GET /drugs`를 add-only 로 연다. **조회(GET /medical-records)는 Epic 4 — 이 스토리 응답은 여전히 POST 결과뿐.**

### 트랜잭션 설계 — 3.1 CTE 확장 (이 스토리의 심장)

기존 `_INSERT_RECORD_AND_COMPLETE`(db/medical_records.py:29-58)에 `rx` CTE 와 최종 SELECT 의 `prescriptions` 집계만 추가한다. **처방을 서비스의 두 번째 db 호출로 쪼개면 커넥션이 달라 원자성이 깨진다**(3.1 과 같은 이유 — 회고 액션 #4의 연장):

```sql
-- db/medical_records.py · _INSERT_RECORD_AND_COMPLETE (3.2 확장 청사진)
with completed as (
    update public.appointment
    set status = '완료'
    where id = %s
      and status = '확정'
      and doctor_id is not null
    returning id, patient_id, hospital_department_id, doctor_id
),
inserted as (
    insert into public.medical_record
        (appointment_id, patient_id, hospital_department_id, doctor_id,
         visited_at, diagnosis, notes)
    select c.id, c.patient_id, c.hospital_department_id, c.doctor_id,
           %s, %s, %s
    from completed c
    returning id, appointment_id, patient_id, hospital_department_id,
              doctor_id, visited_at, diagnosis, notes
),
rx as (
    insert into public.prescription (medical_record_id, drug_id, dosage, days)
    select i.id, x.drug_id, x.dosage, x.days
    from inserted i
    cross join jsonb_to_recordset(%s) as x(drug_id bigint, dosage text, days int)
    returning id, drug_id, dosage, days
)
select i.id, i.appointment_id, i.patient_id, i.hospital_department_id,
       i.doctor_id, i.visited_at, i.diagnosis, i.notes,
       p.name   as patient_name,
       doc.name as doctor_name,
       d.name   as department_name,
       coalesce(
           (select jsonb_agg(jsonb_build_object(
                'id', r.id, 'drug_id', r.drug_id, 'drug_name', dr.name,
                'dosage', r.dosage, 'days', r.days) order by r.id)
            from rx r join public.drug dr on dr.id = r.drug_id),
           '[]'::jsonb) as prescriptions
from inserted i
join public.patient p               on p.id  = i.patient_id
join public.hospital_department hd  on hd.id = i.hospital_department_id
join public.department d            on d.id  = hd.department_id
join public.doctor doc              on doc.id = i.doctor_id
```

- **왜 여전히 한 문장인가:** CAS 0행이면 `inserted`가 비고 `rx`의 `cross join`도 0행 — 아무것도 안 쓰고 `fetchone()` None(기존 409 경로 그대로). `UniqueViolation`(기록 중복)·`ForeignKeyViolation`(없는 drug_id) 어느 쪽이든 **문장 전체 롤백** — 완료 전이·기록·다른 처방이 함께 없던 일이 된다(처방만 빠진 기록·기록 없는 처방이 구조적으로 불가능).
- **처방 0개:** `jsonb_to_recordset('[]')` → 0행 → `rx` 0행 → `jsonb_agg` NULL → `coalesce`가 `'[]'::jsonb` — 응답 `prescriptions: []`. 별도 분기 불필요.
- **파라미터 바인딩:** placeholder 순서는 SQL 그대로 `(appointment_id, visited_at, diagnosis, notes, prescriptions)`(2.3 gotcha — 확인하고 쓸 것). `prescriptions`는 `list[dict]`(키 `drug_id`/`dosage`/`days`)를 **`Jsonb()` 어댑터로 바인딩** — `from psycopg.types.json import Jsonb`, `cur.execute(…, (…, Jsonb(prescriptions)))`. 수동 `json.dumps` 불필요, psycopg 3 표준.
- **jsonb 왕복 타입:** psycopg 는 jsonb 컬럼을 파이썬 `list[dict]`로 파싱해 돌려준다 — `row["prescriptions"]`는 이미 리스트다. `jsonb_to_recordset`의 `days int` 캐스트는 JSON null → NULL, 숫자 → int 로 안전.
- **처방 순서:** `order by r.id` — 단일 INSERT…SELECT 의 identity 는 입력 배열 순서대로 붙으므로 응답·조회가 입력 순서를 유지한다(데모 충분, 결정적).
- **drug 조인은 rx 서브쿼리 안에서만** — 기록 자체의 표시 조인 4개(3.1)는 무수정.

### 서비스 가드 체인 (기존 ①~⑥ 무변경 + 처방 가드 삽입)

`create_medical_record`(services/medical_records.py:14-83)의 기존 가드 ①(빈 진단명 400)→②(404)→③(상태 400)→④(doctor null 400)는 **순서·문구 그대로**. 추가분:

- **④' 일수 가드(④ 다음, db 호출 전):** `if any(p.days is not None and p.days < 1 for p in payload.prescriptions):` → **400** "처방 일수는 1 이상의 숫자로 입력해 주세요." (DB `days`엔 CHECK 없음 — 앱이 규칙 소유, 3.1 의 diagnosis 규칙과 같은 원리. **Pydantic `ge=1` 금지** — 422 list detail 은 일반 메시지로 붕괴되는 확립 패턴.)
- **db 호출:** `insert_medical_record_and_complete(payload.appointment_id, visited_at, diagnosis, payload.notes, [p.model_dump() for p in payload.prescriptions])`.
- **⑤' FK catch(UniqueViolation catch 와 형제):** `except ForeignKeyViolation as exc:` → **400** "선택한 약을 찾을 수 없어요. 약을 다시 선택해 주세요." — import 는 `from psycopg.errors import ForeignKeyViolation, UniqueViolation`. 이 문장에서 클라이언트가 넣는 FK 는 `drug_id`뿐이라(나머지는 예약 행 복사) 위반 = 사실상 없는 약(재시드·id 이동). appointments 의 patient FK catch(services/appointments.py:66-73)와 같은 논리·스타일.
- **drug 존재 pre-check SELECT 를 추가하지 말 것** — FK RESTRICT 가 원천 차단, catch 400 으로 충분(3.1 의 "기록 존재 pre-check 금지"와 같은 원리).
- 매핑: `_to_medical_record_out`에 `prescriptions=[PrescriptionOut(**p) for p in row["prescriptions"]]` 한 줄.

### 실측 스키마 (2026-07-24 라이브 Supabase introspection — 이것이 진실)

```text
prescription: id bigint PK(identity) · medical_record_id bigint NOT NULL (FK→medical_record ON DELETE CASCADE)
            · drug_id bigint NOT NULL (FK→drug ON DELETE RESTRICT)
            · dosage text NULL · days integer NULL
drug: id bigint PK(identity) · name text NOT NULL · unit text NULL
행수(2026-07-24): prescription 0 · drug 4(시드) · appointment 0 · medical_record 0
```

- `dosage`·`days`는 **DB nullable, CHECK 없음** — "약만 필수"는 AC 원문 그대로이고(발명 금지), days≥1 은 앱 레벨 가드다.
- `prescription`에 **유니크 제약 없음** — 같은 약 2행도 DB 는 허용한다. AC 에 금지가 없으므로 **막지 않는다**(발명 금지).
- FK `ON DELETE`: 기록 삭제 시 처방 CASCADE(검증 데이터 원복이 쉬움), 약 삭제는 RESTRICT(처방이 있으면 못 지움 — 이력 보호).
- RLS 는 001_rls.sql 이 이미 prescription·drug 포함 9테이블 ON — **새 마이그레이션·시드 변경 0개.**
- 시드 약 4행: `타이레놀정 500mg(정)`·`아목시실린캡슐 250mg(캡슐)`·`이부프로펜정 200mg(정)`·`세티리진정 10mg(정)` (db/seed/004_seed.sql:70-74).

### 응답 모델 확장 — AD-10 해석 (중요)

`MedicalRecordOut`에 `prescriptions: list[PrescriptionOut] = []`를 추가한다. AD-10 의 "nested 금지"는 **다:1 연관을 객체로 싣지 말라**는 규칙(예: doctor 객체 대신 `doctor_id`+`doctor_name`)이고, 처방은 기록에 **합성(1:N, CASCADE)된 자식 컬렉션**이라 리스트가 유일한 정합 표현이다 — 대신 **리스트의 각 항목이 flat 규칙을 지킨다**(`drug_id` + `drug_name`, drug 객체 중첩 금지). 이 확장으로 Epic 4 의 `GET /medical-records`(FR-11 "진단·처방 포함")가 **같은 정규 모델 하나**를 그대로 재사용한다 — 리소스당 모델 1개 원칙이 유지된다. `PrescriptionCreate`/`PrescriptionOut`은 별도 리소스가 아니라 medical_records 스키마 파일 안의 하위 모델로 둔다(별도 라우터·서비스 없음).

- **자리:** 3.1 이 예약해 둔 위치 — 진료 일시 필드 다음, "저장 순간…" 안내문 앞(같은 `<form>` 안, 제출 시 기록과 함께 저장 — 처방만 따로 저장되는 UI 아님).

- **a11y(UX-DR9):** 칼럼 라벨 행은 시각용 — 각 입력엔 행 번호 포함 라벨(sr-only 가능: `처방 1 약`·`처방 1 용법·용량`·`처방 1 일수`), 삭제는 `aria-label="처방 1 삭제"`. 오류는 `aria-invalid` + `aria-describedby` 로 해당 필드에 연결, `role="alert"`.
- **행 상태:** `{key, drugId: string, dosage: string, days: string}` 배열 + 증가 카운터 key(index 를 key 로 쓰지 말 것 — 중간 삭제 시 입력값이 밀린다). 일수는 텍스트 Input + `inputMode="numeric"`(목업 준수 — type=number 의 스핀 UI·e 표기 문제 회피).
- **제출:** 진단명 검증(기존) → 행별 검증(약 미선택·일수 비정상 — 위 AC4 문구) → 전부 통과 시 `prescriptions: rows.map(r => ({drug_id: Number(r.drugId), dosage: r.dosage.trim() || null, days: r.days.trim() ? Number(r.days) : null}))`. 실패 행이 있으면 서버 미도달.
- **빈 상태(행 0개):** "추가된 처방이 없어요. 처방 없이 저장할 수 있어요." — 목업의 `.empty-rx` 클래스는 문구 없이 스타일만 있어 **이 문구는 이 스토리가 저작**한 것(UX 스펙 gap).
- **저장 성공/실패:** 기존 골격 그대로(toast·목록 복귀·실패 시 reloadNonce). 400 "선택한 약을 찾을 수 없어요…"는 toast 로 그대로 노출(request 가 detail 전달).

### 핵심 안티패턴 (하지 말 것)

- ❌ **처방 INSERT 를 두 번째 db 호출/루프 executemany 로 쪼개기** — 커넥션·문장이 갈려 원자성 파괴. `rx` CTE 하나로 끝(위 청사진).
- ❌ **drug 존재 pre-check SELECT** — FK RESTRICT 가 원천, `ForeignKeyViolation` catch 400 으로 충분.
- ❌ **Pydantic 에 `ge=1`·`min_length`·필수 dosage** — 도메인 규칙은 서비스 400 한국어(확립 패턴). 스키마는 타입·`extra="forbid"`만.
- ❌ **dosage/days 필수화·중복 약 차단 등 요구 발명** — AC 는 "약 선택"만 필수. DB nullable 이 진실.
- ❌ **`_blank_str_to_none` 3번째 사본** — 같은 파일 모듈 레벨로 승격해 notes·dosage 공유. **patients.py 는 이 스토리에서 건드리지 않는다**(공유 모듈 추출은 별도 정리 스토리).
