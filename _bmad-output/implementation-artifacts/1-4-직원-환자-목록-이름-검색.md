## Story

### `GET /patients?search=` 설계 — 이 스토리가 확정하는 계약
- **경로·모양:** `GET /patients`, `response_model=list[PatientOut]`. 성공=`PatientOut` 리스트 JSON 그대로(커스텀 봉투 없음, 200). **`POST /patients`가 돌려주는 것과 완전히 같은 리소스 모델** — 리소스당 정규 모델 1개(AD-10). 리스트 전용 축약 모델을 새로 만들지 말 것.
- **검색 파라미터:** `?search=` **쿼리 파라미터**(경로 세그먼트 아님). 값 없음/공백이면 **전체 목록**, 값 있으면 **이름 부분 일치**. 이름 외 필드(연락처 등) 검색은 스펙 밖(하지 않음).
- **부분 일치 SQL(⚠️ 파라미터화 필수):** `where name ilike %s`에 파라미터 `f"%{term}%"`. **문자열 포매팅(f-string으로 SQL 자체를 조립)·`.format`·`+` 금지 — injection.** psycopg `%s` 파라미터만(1.3 `insert_patient`와 동일 규약). `ILIKE`는 한글엔 대소문자 개념이 없어 `LIKE`와 동일하게 부분 일치하고, 라틴 문자 검색에도 대소문자 무관이라 안전한 기본값.
  - *(권장 하드닝, 선택)* 사용자가 `%`·`_`를 입력하면 와일드카드로 동작한다. 정확히 하려면 term에서 `\` → `\\`, `%` → `\%`, `_` → `\_`로 escape(Postgres ILIKE 기본 escape는 `\`). 데모 범위엔 escape 없이도 무방하나, 넣으면 "홍%길동" 같은 입력이 그대로 리터럴 검색된다.
- **정렬:** `order by name, id` — 직원이 이름으로 훑기 좋게 이름 정렬(동명 tie-break로 id). `refdata`는 `order by id`지만 이 목록은 사람이 이름으로 스캔하므로 name 우선. (한글 정렬이 DB collation에 의존해 애매하면 `order by id`가 안전한 폴백.)
- **환자 스코핑 없음:** 이건 **직원 전체 접근**(FR-3) 화면이라 `?patient_id=` 필터를 쓰지 않는다. `?patient_id=`는 환자용 조회(AD-8, Epic 4)의 규약이고, 여기선 `?search=`(직원 도구)다. 둘을 혼동하지 말 것.
- **1.5가 이 엔드포인트를 재사용:** Story 1.5(환자 신원 선택)의 AC가 *"등록 환자 목록(Story 1.4의 `GET /patients` 재사용)"*이라고 명시한다 → 검색 없이 호출하면 **전체 환자**를 반환하도록 설계(기본 동작). 1.5용 별도 엔드포인트를 만들 필요 없음.

### API 계약 (AD-10) — 이 스토리가 따르는 형태
- 성공 = `list[PatientOut]` JSON, **200**. 각 원소는 `{id, name, birth_date, gender, phone}` flat(정수 id, 날짜 ISO). `POST`가 돌려주는 단건과 **같은 모양**.
- 오류 = HTTP status + `{"detail": ...}`. 이 스토리는 순수 조회라 도메인 거부(4xx 검증)가 없다 — 인프라 500(DB 다운 등)만 있고, 그건 1.2의 전역 예외 핸들러가 이미 한국어 `{detail}`로 매핑한다(추가 작업 없음).
- 프런트는 오직 `lib/api.ts`의 `api.getPatients`만 통해 호출. 컴포넌트에서 직접 `fetch` 금지(AD-1, AD-10).

### 계층 규약 (AD-1·AD-2) — 위반 = 리뷰 반려
- **DB 커넥션은 `app/db/patients.py`에서만** 연다. 라우터·서비스에서 커넥션·SQL 금지. `routers`=HTTP·쿼리 파라미터 수령, `services`=검색어 정규화·`PatientOut` 매핑, `db`=유일한 SQL I/O.
- **상향 import 금지**(db가 services/schemas import 금지). `fetch_patients`는 `dict` 리스트만 반환하고, 서비스가 `PatientOut`으로 매핑(refdata와 동일).
- **검색어 trim/빈값 정규화는 서비스가 소유**(라우터는 원값을 넘기고, 서비스가 `""`/공백 → `None`으로 정리해 db에 넘긴다).

### 프런트 규약 & ⚠️ Next.js/shadcn 특이점
- **⚠️ 이 Next.js는 훈련 데이터와 다르다(16.2.10).** `frontend/AGENTS.md`: *"코드 작성 전 `node_modules/next/dist/docs/`(특히 `01-app`)의 관련 가이드를 읽어라."* 목록 화면은 `staff/patients/new/page.tsx`처럼 **`"use client"` + `useState`/`useEffect` + `api` 호출** 패턴(이미 동작하는 참조 구현)을 따르면 안전.
- **⚠️ shadcn = `base-nova` style on `@base-ui/react`(Radix 아님).** `components.json` 확인됨. 컴포넌트는 반드시 `npx shadcn@latest add table skeleton`으로 생성(손으로 Radix/헤드리스 import 금지). 현재 `button·card·input·label·select·sonner`만 있음 → `table`·`skeleton` 추가 필요.
- **반응형(AC3, UX-DR11):** 한 데이터로 두 표현. `≥md`는 밀도 표, `<md`는 카드. 표준 패턴 — 표는 `<div className="hidden md:block">`, 카드는 `<div className="grid gap-3 md:hidden">`로 감싸 CSS 브레이크포인트로 토글(JS 뷰포트 감지 불필요). 표 컬럼(직원 밀도): 이름·생년월일·성별·연락처.
- **로딩(UX-DR7):** shadcn `Skeleton` 행을 데이터 도착 전 표시. 데이터 오면 대체.
- **빈 상태(AC4, UX-DR7) — 2종 구분:**
  - 등록 환자가 0명(검색 안 함): *"등록된 환자가 없어요. 새 환자를 등록해 주세요."* + `[신규 환자 등록]` 버튼 → `/staff/patients/new` (EXPERIENCE State Patterns "환자 없음").

- **검색 입력(EXPERIENCE Component Patterns "환자 검색"):** 이름 입력 → **디바운스(~300ms)** 후 `getPatients(term)` 호출(서버 필터, AC2). 매 키 입력마다 즉시 호출하지 말 것. 인풋엔 접근 가능한 라벨(`<Label>` 또는 `aria-label="환자 이름 검색"`) 부여(UX-DR9, 모든 입력 라벨).
- **행 클릭 상세 이동은 이 스토리 밖:** EXPERIENCE는 "결과 행 클릭 → 환자 상세"를 언급하지만 **환자 상세/환자별 조회는 Story 4.2**다. 1.4는 목록·검색 **표시**까지 — 행은 표시 전용(상세 라우트 타깃 아직 없음). 1.5(신원 선택)·4.2(직원 조회)가 각자 이 목록을 재사용/확장한다.
- **성별 역매핑:** DB `M`/`F`/null → UI `남`/`여`/`—`. 1.3이 저장 방향(남→M·여→F)을 확정했고, 이 스토리가 **첫 표시 지점**이라 역매핑을 여기서 못 박는다(Story 4.2 조회에서 재사용). ❌ DB의 `M`/`F`를 그대로 화면에 노출하지 말 것.

### Project Structure Notes

  routers/patients.py      # ← UPDATE(추가): GET /patients (search 쿼리 파라미터)

  main.py                  # ← 변경 없음(patients 라우터 이미 마운트)
backend/tests/test_patients.py   # ← UPDATE(추가): GET 계약 테스트
frontend/
  lib/api.ts               # ← UPDATE(추가만): api.getPatients(search?)
  app/staff/page.tsx       # ← UPDATE: "환자 목록·검색" 카드를 /staff/patients 링크로
  app/staff/patients/page.tsx      # ← 신규: 목록 화면("use client", 표/카드·검색·빈 상태)
  components/ui/{table,skeleton}.tsx  # ← shadcn add 생성물

### 이전 스토리 인텔리전스 (1.1~1.3에서 이어받는 것)
- **1.3이 `patient` POST 3계층·`Patient` 타입·등록 폼·toast 인프라를 세웠다.** 이 스토리는 그 위에 GET·목록을 얹는다 — `schemas/patients.py`의 `PatientOut`, `lib/api.ts`의 `Patient` 타입·`request` 헬퍼, `layout.tsx`의 `<Toaster/>`가 전부 재사용 대상.
- **refdata GET이 완벽한 미러:** `get_departments`(라우터)→`list_departments`(서비스)→`fetch_departments`(db)→`DepartmentOut` 매핑, 그리고 `test_refdata.py`(monkeypatch·no-lifespan·flat shape 단언)까지 그대로 patient에 복제하면 된다. [Source: backend/app/{routers,services,db}/refdata.py, backend/tests/test_refdata.py]
- **`getDepartments` 정규화 교훈:** `lib/api.ts`가 이미 `Array.isArray(data) ? data : []`로 비배열 응답을 방어한다 → `getPatients`도 같은 정규화를 넣어 화면이 무한 로딩/크래시에 빠지지 않게.
- **shadcn 특이점(1.3 실측):** Base UI 컴포넌트는 반드시 `shadcn add`로 생성(1.3에서 손으로 넣었다면 Select `items` 라벨 버그를 겪었을 것). `table`·`skeleton`도 CLI로.
- **검증 문화(사용자 선호·메모리):** "완료"는 테스트 통과 + **브라우저에서 눈으로 관통 확인**(헤드리스 스크린샷). 1.1~1.3 모두 이 방식으로 마감. [Source: feedback-verify-browser-render]
- **커밋/작업 상태 주의:** 1.3의 산출물(patients 4파일·등록 폼 등)은 **아직 커밋되지 않은 워킹 트리 변경**일 수 있다(sprint-status는 done). 코드가 실제로 존재함을 먼저 확인하고 그 위에 얹을 것. `main` 브랜치 기준.
