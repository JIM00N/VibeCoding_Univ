## Story

As a 접수 직원,
I want 예약 관리에서 환자를 골라 대신 예약을 잡기를,
so that 전화·방문으로 온 환자의 예약을 직원이 직접 생성한다.

**한 줄 성격:** **순수 프런트·add-only.** 백엔드는 이미 다 있다 — `POST /appointments`(2.1)·`GET /patients?search=`(1.4)·`GET /departments`·`GET /doctors?hospital_department_id=`(2.1) 네 개면 끝이고 `lib/api.ts`에도 필요한 메서드가 전부 있다. **신규 마이그레이션·백엔드·API 클라이언트 메서드 0.** 만드는 것은 둘 — ① 대리 예약 다이얼로그 컴포넌트(`components/proxy-booking-dialog.tsx` — 환자 검색·선택 + 진료과·의사·날짜·30분 슬롯 + 제출), ② 슬롯 시각 헬퍼(`lib/booking-slots.ts` — 서울 고정 30분 격자). 기존 예약 관리 페이지에는 **[대리 예약] 버튼과 다이얼로그 배선만** 얹는다(약 10줄).

## Acceptance Criteria

**AC1 — 진입: 예약 관리의 [대리 예약] 다이얼로그 (FR-18, 사용자 결정 2026-07-26)**
**Given** 직원이 예약 관리(`/staff/appointments`)에 있을 때
**When** 제목 옆 **[대리 예약]** 버튼을 누른다
**Then** 목록 위에 대리 예약 **다이얼로그**(비파괴적 모달 1단계, `components/ui/dialog`)가 열리고, 목록 화면·좌측 사이드바 컨텍스트를 잃지 않는다
**And** 예약이 0건인 빈 상태에서도 같은 진입을 제공한다(빈 상태 버튼)

**AC2 — 환자 선택: Story 1.4 검색 재사용 (FR-18)**
**Given** 대리 예약 다이얼로그가 열렸을 때
**When** 환자 이름 일부를 입력한다
**Then** `GET /patients?search=`로 **서버측** 부분 일치 검색(디바운스 250ms, 클라이언트 배열 필터 아님)한 결과에서 환자를 고르고, 고른 환자는 선택 상태로 표시되며 [변경]으로 다시 고를 수 있다
**And** 로딩(Skeleton 또는 로딩 문구)·**조회 오류**·**검색 결과 0건**을 서로 구분해 표시한다(오류를 빈 상태로 렌더하지 않는다 — 1.4 규율)

**AC3 — 예약 생성: Story 2.1 폼·계약 재사용 (FR-18, FR-6 P0)**
**Given** 환자를 고른 상태에서
**When** 진료과 → 담당 의사 → 날짜 → 30분 슬롯을 고르고 제출한다
**Then** `POST /appointments`로 `status=대기`·`doctor_id`가 채워진 예약이 생성된다(2.1과 동일 계약 — 신규 엔드포인트·신규 도메인 로직 0)
**And** `reserved_at`은 30분 경계(분 ∈ {0,30}, 초 0)의 ISO-8601 UTC로 전송돼 서버 `to_slot()`·DB CHECK를 그대로 통과한다(AD-3, AD-9)
**And** 슬롯 셀은 available/selected 2상태이고 각 셀에 한국어 SR 라벨·키보드 조작이 있다(`components/slot-picker` 재사용, UX-DR3·UX-DR9)

**AC4 — 성공: toast + 목록 즉시 반영 (UX-DR7, UX-DR2, 사용자 결정 2026-07-26)**
**Given** 대리 예약 저장에 성공했을 때
**When** 응답이 온다
**Then** 다이얼로그가 닫히고 성공 toast가 뜨며, **생성된 예약이 목록 맨 위에 `대기` 배지로 즉시 나타난다**(POST 응답 행을 목록 상태에 prepend — 목록 정렬 `id desc`와 일치, 전체 재조회 없이도 반영)
**And** 그 행에서 기존 [확정]·[취소]·[의사 변경] 액션(2.2·2.3)이 그대로 동작한다(회귀 0)

**AC5 — 검증·오류 (UX-DR9, UX-DR10, AD-10)**
**Given** 환자·진료과·담당 의사·시간 중 하나라도 비었을 때
**When** 제출을 시도한다
**Then** 서버에 도달하기 전에 **라벨과 연결된 인라인 오류**(`aria-invalid`·`aria-describedby`·`role="alert"`)로 막는다
**And** 서버가 4xx를 주면 `{"detail": …}` 한국어 메시지를 그대로 toast로 보여준다(직원 톤 = 간결). 실패해도 다이얼로그 입력은 남아 다시 시도할 수 있다

**AC6 — 셸·반응형·역할 정합 (UX-DR11, UX-DR12, UX-DR4)**
**Given** 데스크톱(≥md)과 모바일(390×844)에서
**When** 다이얼로그를 연다
**Then** 다이얼로그 내용이 뷰포트를 넘지 않고 **안에서 스크롤**되며(390×844에서 [예약] 버튼까지 도달 가능), 좌측 사이드바는 `예약 관리` 활성을 유지하고 상단 역할 바는 `직원` 그대로다
**And** 역할 바에 선택 환자 이름을 **넘기지 않는다** — 대리 예약의 환자는 폼 입력값이지 직원의 신원이 아니다(UX-DR4·AD-8 경계)

**AC7 — 회귀 0 · 품질 게이트 (add-only P0.5)**
**Given** 이 스토리가 순수 프런트일 때
**When** 구현한다
**Then** **신규 마이그레이션·백엔드·`lib/api.ts` 메서드 0**(라이브 DB·FastAPI 무변경 — 최우선 금기). 환자·의사 화면과 기존 직원 3화면 **회귀 0**
**And** `npm run lint`·`npm run build` 그린 · 백엔드 `pytest -q` 전체 그린(회귀) · 실 Supabase **curl 실증**(로컬 uvicorn) · **브라우저 실측**(390×844 + ≥md, 콘솔 0) · **생성한 검증 예약은 SQL로 원복**

## Dev Notes

### 🎯 이 스토리의 한 줄 요약

**백엔드는 이미 완성돼 있다.** `POST /appointments`는 `patient_id`를 요청 바디로 받는다 — 환자 본인이 보내든 직원이 보내든 계약이 같다. 그래서 6.3은 **"직원이 환자를 고르는 UI"** 하나만 새로 만들면 끝난다. 신규 마이그레이션·백엔드·API 클라이언트 메서드 **0**, 신규 도메인 로직 **0**.

### 왜 "이미 준비돼 있다" 인가 — 선행 스토리가 남긴 훅

- **2.1**이 `POST /appointments`(status=대기·`doctor_id` 필수·`to_slot()` floor·의사↔진료과 소속 검증)와 프런트 예약 폼(진료과→의사→날짜→30분 슬롯)의 정본을 남겼다. → 6.3은 **같은 계약을 다른 화면에서 호출**할 뿐이다. `lib/api.ts`의 `createAppointment`·`getDepartments`·`getDoctors`가 그대로 쓰인다(신규 메서드 0).
- **1.4**가 `GET /patients?search=`(서버측 부분 일치) + 250ms 디바운스 + "로딩/오류/빈 상태 3분기" 규율을 남겼다. → 환자 선택기는 이 검색을 **그대로 재사용**(`api.getPatients(search)`).
- **2.3**이 예약 관리 페이지 안의 **폼 다이얼로그**(base-ui `Dialog` + 안에 `Select` + 열릴 때 상태 리셋 + 비관적 저장 + 실패 시 재동기화)의 정본을 남겼다. → 대리 예약 다이얼로그는 이 구조의 형제다.
- **2.2**가 목록 상태를 **응답 행으로 갱신**하는 패턴(`setAppointments(prev => prev.map(...))`)을 남겼다. → 생성은 그 짝인 **prepend**(`[appt, ...prev]`)면 충분하다(목록 정렬 `id desc`와 일치).
- **6.2**의 사이드바 활성 판정이 `pathname.startsWith("/staff/appointments")`라, 다이얼로그 방식은 **경로가 안 바뀌어** 활성 표시에 아무 영향이 없다(`staff-sidebar.tsx` 무수정).

### 설계 결정

1. **다이얼로그 방식(사용자 결정 2026-07-26).** 별도 페이지(`/staff/appointments/new`)가 아니라 예약 관리 목록 위 모달 — 목록 컨텍스트를 잃지 않고, 저장 즉시 뒤에 있는 목록에 반영되는 것을 눈으로 본다(AC4). 비파괴적이므로 `AlertDialog`가 아니라 `Dialog`(2.3 의사 변경과 동일 급). 대가는 **높이** — 기본 `DialogContent`(`max-w-md`, 높이 무제한)를 그대로 쓰면 모바일에서 버튼이 화면 밖으로 나가므로 `max-w-lg max-h-[85vh] overflow-y-auto`가 **필수**다(AC6, 실측 항목).
2. **다이얼로그는 별도 컴포넌트 파일로.** `app/staff/appointments/page.tsx`는 이미 509줄이고 다이얼로그 2개를 갖고 있다 — 세 번째 폼을 인라인하면 그 파일이 700줄을 넘고 리뷰·회귀 위험이 커진다. `components/proxy-booking-dialog.tsx`가 폼 전부를 소유하고, 페이지는 **버튼 + 배선 ~10줄**만 얹는다(add-only 최소 접촉면).
3. **목록 반영은 prepend(재조회 아님).** 서버 목록이 `id desc`라 방금 만든 예약이 항상 맨 위 — POST 응답 행 하나를 앞에 붙이면 정렬·표시 필드가 모두 정합한다. 전체 재조회(`reloadNonce`)는 불필요한 왕복이고, 그 사이 다른 행의 낙관적 상태를 날린다. *(실패 경로에서 목록 재동기화하는 2.2 패턴은 여기 해당 없음 — 생성 실패는 목록을 stale하게 만들지 않는다.)*
4. **환자는 폼의 첫 필드.** 결과 0건일 때 안내하는 `/staff/patients/new` 링크는 다이얼로그를 벗어나 **입력을 잃는다**. 환자를 맨 위에 두면 이탈 시점에 잃을 입력이 사실상 없다. *(대안: 다이얼로그 안에서 환자 등록까지 — 모달 2단계라 UX-DR6 "모달 1단계" 위배, 기각.)*
5. **슬롯 시각 헬퍼는 신규 `lib/booking-slots.ts`(2번째 사본, 의도적).** 서울 tz 고정 로직은 "왜"가 붙은 미묘한 코드라 인라인 복사보다 이름 있는 모듈이 낫다. `app/patient/book/page.tsx`를 import로 이관하지 **않는 이유**: 그 파일은 동결(add-only 규율)이고, 중복 통합은 Epic 3 회고 액션 #2의 정리 스토리 몫이다(`formatReservedAt` 2-소스와 같은 처리 — `deferred-work.md`에 한 줄 기록).
6. **환자 선택은 신규 공용 컴포넌트로 뽑지 않는다.** 지금 사용처가 하나뿐이다. `app/staff/patients/page.tsx`(1.4 목록 화면)를 "선택 모드"로 개조하는 것도 금지 — 동작 중인 조회 화면에 모드 분기를 넣는 건 회귀 위험 대비 이득이 없다.
7. **P0 경계 유지 — 가용성 검사 없음.** 직원 대리 예약도 2.1과 똑같이 (의사, 슬롯) 충돌을 **검사하지 않는다**. `taken` 셀·red 인라인 거부는 Epic 5.1이 세 쓰기 경로(예약 생성·의사 변경·walk-in)에 한 번에 얹는다. 여기서 미리 만들면 5.1의 단일 관문(`check_and_occupy`, AD-4)이 깨진다.
