# 적대적 리뷰 — hospital-care PRD

## 종합 판정

이전 리뷰 반영으로 슬롯 규칙(30분 격자)·FR-6 자기모순·P0/P1 분리 같은 큰 지뢰는 대부분 밟고 지나갔고, 스키마 정합성 의식도 평균 이상이다. 그러나 **핵심 판매 포인트인 "가용성 불변식(의사·슬롯 유일)"은 DB에서 전혀 강제되지 않는 앱-레벨 희망사항**이고, **P0 범위 정의가 FR-6의 "항상 의사 배정" 불변식·주요 사용자 여정과 정면충돌**해 개발자가 P0만 짜면 문서상 경로가 성립하지 않는다. 여기에 walk-in의 미명세 구멍(부서 출처·"대기 처리")과 3일/1인 풀스택 마감 리스크가 얹혀, "끝까지 관통"이라는 목표 자체가 P1 구간에서 조용히 깨질 여지가 크다.

발견 건수: **critical 0 · high 2 · medium 7 · low 3 (총 12)**

## Findings

- **[high]** P0 범위가 FR-6 "항상 의사 배정" 불변식을 깨고 FR-9를 막는다 (§4 P0 정의 vs FR-6·FR-9, schema L92/L109, addendum A3) — P0는 "FR-6에서 가용성·**자동배정을 뺀** 기본 예약 생성"이다. 그런데 FR-6 본문은 "예약에는 **항상** 담당 의사가 배정된다"고 못 박고, 자동배정은 P1로 뺐다. 결과: P0에서 환자가 의사를 비우면 `appointment.doctor_id`는 그냥 **null로 남는다**(자동배정 없음). 그런데 FR-9/진료기록은 `medical_record.doctor_id NOT NULL`(schema L109, A3)을 요구한다 → **P0 단독으로는 진료 기록을 못 쓴다.** 즉 성공지표 ①의 "예약→진료 확정·의사 배정→기록" E2E가 P0만으로 성립하지 않는다. *제안:* P0 정의에 "의사 미선택 예약은 직원이 기록 작성 전 수동 배정(FR-7 base, 재검사 없이)"을 명시하고, FR-6의 "항상 배정"을 "기록 시점까지 배정되어야 한다"로 완화하라. 또는 최소 자동배정을 P0로 끌어올려라.

- **[high]** 가용성 불변식이 DB에 전혀 강제되지 않는다 — FR-15 "하나만 존재"는 보장이 아니라 기도다 (FR-15, addendum A4 "동시성/무결성", schema 전체) — 시스템의 심장인 "(의사, 슬롯)에 활성 예약/​walk-in 하나만"은 `appointment`·`medical_record` **두 테이블**에 걸쳐 있어 단일 부분 유니크 인덱스로 못 막고, A4가 스스로 인정하듯 **순수 앱-레벨 검사**다. 전형적 TOCTOU 경쟁 조건이며, 특히 FR-6 자동배정("빈 의사를 골라")은 두 요청이 동시에 같은 의사를 집을 수 있다. DB엔 이 불변식을 지키는 제약이 **0개**여서 앱 버그·직접 쿼리·시드 스크립트 한 방이면 조용히 깨진다. NFR-2가 내세우는 "정규화된 모델 위의 정합성"은 정작 이 예약 무결성엔 손도 못 댄다. *제안:* FR-15 본문에 "동시 요청 없는 단일 세션 전제에서만 차단 보장"임을 격하 명시하고, "차단한다"를 그렇게 완화하라. 엄밀성을 원하면 union 뷰 위 EXCLUDE 제약 또는 점유 전용 `slot_occupancy` 단일화를 확장 항목으로 못 박아라.

- **[medium]** walk-in의 진료과 출처가 미명세인데 컬럼은 NOT NULL이다 (FR-16, schema L110, addendum A4 walk-in 항목) — FR-16은 "빈 의사에게 즉시 진료"만 말하고, 예약이 없으니 진료과 선택 단계도 없다. 그런데 `medical_record.hospital_department_id`는 NOT NULL이고 "빈 의사"를 범위 지으려면 **어느 hospital_department인지 먼저 정해져야** 한다. 이 입력이 UJ-2/FR-16 어디에도 없다 → 개발자가 임의로 메꿔야 하는 구멍. *제안:* FR-16에 "walk-in 시 직원이 진료과를 먼저 선택하고 그 과의 빈 의사를 배정한다"를 추가하라.

- **[medium]** "다른 시각 안내 또는 대기로 처리"의 '대기'는 뒷받침 데이터가 없는 dangling path (FR-16 말미, §4 제외 목록) — walk-in 빈 의사 없을 때 "대기로 처리"라는데, §4는 **"대기열"을 명시적으로 제외**했다. 대기 상태를 담을 엔티티도, 완료 기준도 없다 → 검증 불가능한 문구, 개발자는 구현 대상이 없어 헤맨다. *제안:* "대기 처리"를 지우고 "빈 의사 없으면 거부 메시지 표시로 종료"로 확정하라. 대기열이 필요하면 별도 FR·엔티티로 승격.

- **[medium]** 주요 사용자 여정이 P1 기능으로 서술돼 P0 구현자를 오도한다 (UJ-1 step2, UJ-2 step3 vs §4) — UJ-1의 핵심 동선("비워두면 **자동으로 배정**")과 UJ-2의 "배정된 담당 의사를 확인"은 전부 **P1(FR-6 자동배정)** 에 의존한다. P0부터 관통하라는 가드레일을 따르면 문서화된 유일한 여정이 P0에서 성립하지 않는다 → "P0에서 사용자는 뭘 보는가" 시나리오가 없다. *제안:* UJ 각 스텝에 (P0)/(P1) 태그를 달거나, P0용 수동배정 경로를 병기하라.

- **[medium]** RLS posture가 아직 존재하지 않는 마이그레이션에 걸려 있고 DB는 이미 "배포 완료"됐다 (NFR-4, addendum A1 ⚠️ 경고, A2) — A1 스스로 경고하듯 `schema.sql`엔 RLS 구문이 없고, A2는 이 스키마가 이미 Supabase에 "배포 완료"라고 한다. 즉 **지금 배포된 DB는 RLS OFF** 상태이며, NFR-4의 잠금은 아직 안 짜인 별도 마이그레이션에 의존한다 — 3일 마감에 빠뜨리기 딱 좋은 항목. 게다가 프런트는 Supabase를 직접 안 부르므로(NFR-3) anon 키가 번들에 실릴 일이 없어 "anon 차단"의 실효는 방어적 의미에 그친다. *제안:* RLS 활성화 마이그레이션을 **배포 뼈대(NFR-1)와 같은 초기 산출물**로 태스크화하고, "완료" 정의에 "9개 테이블 RLS ON 확인"을 넣어라.

- **[medium]** "선택된 환자의 데이터만 보인다"는 격리 언어가 실제 노출을 가린다 (FR-2, 성공지표 ③, addendum A1-5) — 로그인이 없어 환자 목록이 **전원의 이름·생년월일을 아무에게나 나열**하고, API 필터는 클라이언트가 준 `patient_id`로 도는지라 방문자가 아무 환자나 골라 그 사람의 진단·처방을 전부 열람할 수 있다. 의도된 축소지만 FR-2/성공지표의 "~데이터만 보여준다"는 표현은 이를 **격리처럼 오독**하게 만든다(A1엔 caveat이 있으나 본문 FR엔 없음). *제안:* FR-2에 "이는 기밀 격리가 아니며 데모상 누구나 임의 환자를 선택·열람할 수 있음"을 한 줄 명시.

- **[medium]** 예약:기록 1:1 미강제 + 완료 전이 트리거가 반쪽짜리 (FR-8, FR-9, addendum A3 L40) — `medical_record.appointment_id`에 UNIQUE가 없어(A3 인정) 한 예약에 기록 2건·재작성·중복 완료전이를 막는 가드가 없다. 게다가 FR-8 완료 전이는 "예약에 기록 작성 시"인데 **walk-in 기록은 appointment_id가 null**이라 이 규칙 밖(정상 예약에만 적용). 또 앱이 기록 저장 시 `appointment.status='완료'`를 손수 갱신해야 하는데 이 "쓰기 부작용"이 어느 FR에도 명시 안 됨. *제안:* "정상 예약 기록 저장 트랜잭션에서 appointment.status를 완료로 갱신"을 FR-8/FR-9에 명시하고, '예약당 기록 1건' 앱 가드를 완료 기준에 포함하라.

- **[medium]** 3일·1인·풀스택에 교차테이블 가용성 엔진+walk-in까지 — P1 미착륙 위험 (§10 상단 유형/마감, §4 P1) — 생성 07-12, 마감 07-16(목), 오늘 07-13 기준 **실질 3일**. P1(FR-15 교차테이블 union 충돌검사 + FR-6 자동배정 + FR-16 walk-in + FR-7 재검사)은 가장 버그가 몰리는 fiddly 구간이다. 가드레일(넓이<관통)은 훌륭하나, 성공지표 ①이 "진료 확정·**의사 배정**"을 핵심으로 걸어놔서 P1이 빠지면 데모의 킬러 장면이 사라진다. *제안:* "P1 미완 시에도 성공으로 인정되는 최소 데모(수동 배정 E2E)"를 성공지표에 명시해 마감-품질 트레이드오프를 사전 합의하라.

- **[low]** 과거·비경계 시각 예약을 막는 게 앱-레벨뿐 (FR-6, addendum A4, schema L93) — `reserved_at`가 30분 경계인지, 과거가 아닌지 강제하는 CHECK가 없다. 앱 버그 하나면 03:17 예약·어제 예약이 그대로 저장된다. 슬롯 키 floor 계산은 서버 타임존 의존(Railway 기본 UTC 가능) — 30분 정렬 자체는 UTC/KST가 어긋나지 않으나 표시·기록 시각 일관성은 명시 고정이 안전. *제안:* "과거 슬롯 예약 거부"를 FR-6에, 슬롯 계산 기준 타임존(UTC 저장·슬롯 단위 비교)을 A4에 한 줄씩 고정.

- **[low]** NFR이 제품 특유 임계치 없이 보일러플레이트에 가깝다 (§6 NFR-1~5) — 응답시간·동시성·데이터량 등 정량 임계치가 없고, NFR-5 "브라우저에서 눈으로 끝까지 확인 가능"은 측정 기준이 없는 서술이라 "완료" 판정을 흐릴 여지가 있다(과제 규모상 치명적이진 않음). *제안:* NFR-5를 "UJ-1·UJ-2 각 스텝이 배포 URL에서 클릭만으로 완주됨"처럼 체크 가능한 문장으로 바꿔라.

- **[low]** 완료 예약의 즉시 슬롯 해제 규칙이 walk-in 점유와 비대칭 (addendum A4 "점유 대상" 항목) — 정상 예약이 완료되면 슬롯이 즉시 풀리지만 walk-in 기록은 영구 점유로 계산된다. 같은 슬롯 두 완료 진료가 한쪽만 점유로 잡히는 비대칭이 존재. 과거 슬롯은 미래 충돌과 무관해 과제 규모엔 무해하나, 30분 초과 진료·같은 슬롯 재진입을 확장할 때 함정. *제안:* 확장 노트에 "완료/​walk-in 점유 계산 일원화"를 메모.
