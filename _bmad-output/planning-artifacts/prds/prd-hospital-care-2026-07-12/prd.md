# PRD: 병원 진료관리 풀스택 서비스 (hospital-care)

> 유형: 교육 과제(바이브 코딩) · 1인 개발 · 마감 2026-07-16(목). 목표는 상용 해자가 아니라 **정규화된 데이터 모델 위에서 환자↔병원 전체 흐름이 끝까지 동작하는 풀스택 앱 완성**. 상위 배경은 `../../briefs/brief-hospital-care-2026-07-12/brief.md`, 기술 세부는 `addendum.md` 참조.

## 1. 요약 (Overview)

한 병원의 **환자 접수 → 예약 → 진료 → 진료 기록 → 조회** 흐름을 하나의 웹 서비스로 관리한다. 환자는 스스로 **예약을 잡고 자기 진료 기록을 조회**하고, 병원 직원(접수·의사)은 **환자 등록·예약 관리·진료 기록 작성**을 한 곳에서 처리한다.

**왜(문제).** 접수·예약·진료·기록이 종이차트·전화·분리된 장부로 흩어지면, 직원은 "이 환자가 언제 왜 왔고 무슨 약을 받았는지"를 매번 다시 뒤지고, 환자는 자기 예약·과거 진료를 스스로 확인할 방법이 없어 전화로 묻는다. 진료 기록이 "어느 병원·과에서 있었나"와 분리되면 이력도 왜곡되기 쉽다. 이 서비스는 그 흐름을 한 곳에 모아 끝까지 잇는다.

로그인/인증은 이번 범위에서 구현하지 않고 **역할 선택(환자 / 직원)** 으로 대체한다 — 인증 부담 없이 전체 흐름의 작동 확인에 집중하기 위한 의도적 선택. 데이터는 9개 테이블(ERD 설계·Supabase 배포 완료)을 사용하고, 프런트는 Next.js, 백엔드는 FastAPI, 배포는 **프런트 Vercel · 백엔드 Railway**(아키텍처 단계 결정, 2026-07-13).

## 2. 목표 & 성공 지표

**목표.** 정규화된 9개 엔티티 위에서 환자·직원 양측의 핵심 흐름 한 줄기를 **끝까지 관통**시키고, 실제 URL로 시연 가능하게 배포한다.

**성공 지표 (Success Metrics)**
- ✅ **전체 흐름 end-to-end 동작** — 환자 등록 → 예약 → 진료 확정·의사 배정 → 진료 기록 작성 → 환자/직원 조회가 UI에서 이어진다. *(핵심 지표)*
- ✅ 9개 엔티티가 **ERD의 FK·CHECK 제약대로** 생성/조회/수정된다(실제 Supabase 사용).
- ✅ **역할 선택**에 따라 다른 화면이 뜨고, 환자 화면은 선택된 환자의 데이터만 보인다.
- ✅ **배포 완료 — 프런트 Vercel · 백엔드 Railway** — 공개 URL로 접속·시연 가능.

**역-지표 (Guardrail).** 부가 화면·기능을 넓히려다 **핵심 한 줄기 완성·배포가 지연되면 실패로 본다.** 넓이보다 "한 줄기 관통"이 우선.

> **최소 성공 기준(마감 대비).** P1(자동배정·가용성 충돌 검사·walk-in)이 미완이어도, **P0 E2E**(등록 → 의사 직접 선택 예약 → 확정 → 기록 → 조회)가 배포 URL에서 관통하면 성공으로 인정한다. P1은 그 위에 얹는 안전 강화·편의다.

## 3. 사용자 여정 (User Journeys)

주인공: 🧑‍🦰 **이수민**(예약을 잡으려는 환자) · 🧑‍💼 **박서준**(접수 직원) · 👨‍⚕️ **김민재**(의사 — 독립 역할). 의사는 `[의사]` 역할로 진입해 자기에게 배정된 예약을 연다 *(2026-07-25 correct-course: 서브 페르소나 → 독립 역할 승격. 그 전엔 로그인이 없어 의사도 `[직원]` 화면 안에서 기록했다)*.

### UJ-1 — 이수민(환자)이 예약을 잡고, 나중에 자기 진료 기록을 확인한다
1. 앱에 들어가 역할 선택에서 **`[환자]`** 를 고른다 → 등록된 환자 목록에서 **본인(이수민)을 선택**해 신원을 잡는다. *(로그인 대체)*
2. **진료과**(예: 이비인후과)와 시각을 고르고 **담당 의사를 선택해 예약을 잡는다** *(P0)*. — 의사를 비워두면 **자동 배정**되는 편의는 *(P1)*.
3. 며칠 뒤 다시 들어와 `[환자]` 화면에서 **내 예약 상태**와 **지난 진료 기록**(진단·처방)을 확인한다.
- 성공: 전화 한 통 없이 앱에서 예약·조회가 끝난다.

### UJ-2 — 박서준(직원)이 환자를 맞고, 김민재(의사)가 진료를 기록한다
1. 역할 선택에서 **`[직원]`** 을 고른다.
2. 처음 온 환자면 **신규 환자로 등록**한다(이름·생년월일 등).
3. 들어온 **예약을 확정**하고, 배정된 **담당 의사(김민재)를 확인**한다 — 필요하면 **다른 의사로 변경**하거나 예약을 취소한다. *(의사는 예약 시 이미 배정돼 있음 — FR-6)*
4. 진료 후, 의사가 그 예약에 **진단·처방·소견을 진료 기록으로 작성**한다. 이 기록은 *"어느 진료과에서 있었는지"* 를 스스로 저장한다(이력 보존).
5. 이후 직원은 **환자별 진료 내역 전체를 조회**한다.
- 성공: 종이 장부 없이 한 화면에서 등록→예약관리→기록→조회가 돈다.

## 4. 범위 (Scope)

**포함 — 우선순위로 나눔** (가드레일: *넓이보다 한 줄기 관통 우선*):
- **P0 (핵심 한 줄기 — 먼저 끝까지 관통):** FR-1 ~ FR-5 · **기본 예약**(FR-6에서 가용성·자동배정을 뺀 예약 생성 — **의사는 직접 선택 필수**라 `doctor_id`가 항상 채워져 기록까지 정합) · FR-7(확정/취소/변경) · FR-8 · FR-9 ~ FR-14 · **Railway 배포**(NFR-1) · **9개 테이블 RLS ON**(NFR-4, 배포 뼈대와 함께 초기 산출물).
- **P1 (그 다음 — P0 관통 후 얹는다):** **FR-15**(가용성 충돌 검사) · **FR-6의 자동 배정·충돌 거부** · **FR-16**(walk-in) · FR-7의 재배정 재검사.
- P0/P1은 *제외*가 아니라 **구현 순서**다. P0를 먼저 배포 가능한 상태로 관통시킨 뒤 P1을 안전하게 추가한다.

**제외 (이번엔 안 함):**
- 실제 로그인/인증 (역할 선택으로 대체)
- 병원 선택 (**단일 병원** 전제 — 진료과만 선택)
- 참조 데이터(진료과·의사·약) 관리/편집 화면 (**시드 데이터로만**)
- 결제·수납·보험 청구 / 재고 관리 · 진단서 발급 / 알림(문자·푸시)·대기열 / 모바일 앱 / 고도화 권한·감사 로그

## 5. 기능 요구사항 (Functional Requirements)

### F1. 역할 선택 & 환자 신원
- **FR-1** 첫 화면에서 사용자는 `[환자]` / `[직원]` / `[의사]` 역할을 선택한다. (실제 로그인 없음) *(의사 역할은 2026-07-25 correct-course로 추가 — `sprint-change-proposal-2026-07-25.md`)*
- **FR-1b (의사 진입)** `[의사]` 선택 시 의사 목록에서 본인을 고른다(FR-2 환자 신원 선택의 의사판 — 로그인 대체, 기밀 격리 아님). 이후 의사 화면은 그 의사에게 배정된 예약을 먼저 보여준다.
- **FR-2** `[환자]` 선택 시 등록된 환자 목록에서 본인을 고르고, 이후 환자 화면은 **선택된 환자의 데이터만** 보여준다. *(앱 레벨 필터 — [ASSUMPTION] 신원 선택은 목록에서 이름 선택 방식, 추후 변경 가능)* **주의:** 로그인이 없어 이는 **기밀 격리가 아니다** — 데모상 누구나 목록에서 임의 환자를 선택해 그 환자의 데이터를 열람할 수 있다(진짜 격리는 확장 과제, A1).
- **FR-3** `[직원]` 선택 시 별도 신원 선택 없이 직원 화면(전체 데이터 접근)으로 진입한다.
- **FR-17 (의사 배정 예약 뷰)** 의사 화면은 배정된 활성 예약(대기·확정)을 먼저 보여주고, 진료 기록 작성으로 완료 전이된 예약은 활성 목록에서 빠져 "완료된 진료"로 분류된다. `GET /appointments?doctor_id=&status=…` 앱 레벨 필터(AD-8의 의사판) — 신규 스키마 없음. *(2026-07-25 correct-course)*
- **FR-18 (직원 대리 예약)** 직원이 예약 관리에서 환자를 골라 예약 폼(FR-6 P0 재사용)으로 대리 예약을 생성한다. walk-in 즉시진료(FR-16)와 구분한다. *(2026-07-25 correct-course)*

### F2. 환자 등록 (직원)
- **FR-4** 직원이 신규 환자를 등록한다 — 이름(필수) · 생년월일 · 성별 · 연락처.
- **FR-5** 직원이 환자 목록을 조회하고 이름으로 찾을 수 있다.

### F3. 예약 & 가용성 (Appointment & Availability)
- **FR-6** 환자가 **진료과**와 시각(**30분 슬롯**)을 골라 예약을 생성한다(병원 선택 없음 — 단일 병원). **예약은 담당 의사가 배정된 상태로 존재한다** — **(P0)** 예약 생성 시 담당 의사를 **직접 선택**한다(→ `doctor_id`가 항상 채워져 진료 기록의 `doctor_id NOT NULL`까지 정합). **(P1)** 의사를 비워두면 해당 진료과에서 **시스템이 빈 의사를 자동 배정**하고, 빈 의사가 없으면 그 슬롯은 **예약 불가**. *(가용성 검사·자동배정·거부는 P1 / FR-15.)*
- **FR-7** 직원이 예약을 **확정/취소**하고, 필요 시 담당 의사를 **변경(재배정)** 한다. 재배정 시에도 가용성(FR-15)을 검사한다.
- **FR-8** 예약 상태(**대기 → 확정 → 완료 / 취소**)가 흐름에 따라 갱신되고 목록에서 확인된다. **완료 전이:** 해당 예약에 진료 기록이 작성되면(FR-9) **같은 트랜잭션에서** status가 **완료**로 전이된다(기록 저장의 부작용으로 명시). **한 (정상) 예약에는 진료 기록 1건만** 허용한다 — DB에서 부분 유니크 인덱스로 강제한다(A3). walk-in 기록(`appointment_id` 없음)은 이 완료 전이 대상이 아니다.
- **FR-15 (가용성 규칙)** 예약과 walk-in 진료는 **공통 가용성 단위 (의사, 슬롯)** 을 공유한다(슬롯 = **30분 격자**; walk-in은 진료 시각을 속한 슬롯으로 내림). 한 (의사, 슬롯)에는 활성(대기·확정) 예약 또는 walk-in 진료가 **하나만** 존재하며, 예약 생성·의사 배정/변경·walk-in 생성 시 앱(FastAPI)이 충돌을 차단한다. **강제 수준(정직한 경계):** 충돌 소스가 `appointment`·`medical_record` **두 테이블**에 걸쳐 있어 단일 DB 제약으로는 못 막고 **앱 레벨 검사**로 처리한다 — **동시 요청이 없는 단일 세션 전제에서 차단을 보장**하며, 동시 요청 경쟁(TOCTOU)의 완전 차단은 과제 범위 밖이다. `reserved_at`의 30분 정렬은 DB CHECK로 보강한다(A4). 두 소스를 합친 EXCLUDE 제약/공용 슬롯 뷰는 확장 과제.

### F4. 진료 기록 & Walk-in (직원/의사)
- **FR-9** 확정된 예약에 대해 진료 기록을 작성한다 — 진단명 · 소견 · 진료일시. 기록은 **발생 진료과를 자체 보관**한다(이력 보존). 작성 시점엔 담당 의사가 지정돼 있어야 한다(FR-7 의존).
- **FR-10** 진료 기록에 **처방**을 0개 이상 추가한다 — 약 선택 + 용법·용량 · 처방일수.
- **FR-16 (walk-in 즉시 진료)** 직원/의사가 **예약 없이 온 환자**에 대해 먼저 **진료과를 선택**하고, 그 과에서 현재 슬롯이 빈 의사에게 즉시 진료로 배정해 기록을 남긴다(`appointment_id` 없이 진료 기록 생성 — 발생 진료과는 **배정된 의사의 소속**으로 저장). 이 진료는 해당 **(의사, 슬롯)** 을 점유해 같은 슬롯의 예약을 막는다(FR-15). **그 슬롯에 빈 의사가 없으면 walk-in 불가** — **거부 메시지를 띄우고 종료**한다(다른 시각 안내). *(대기열은 범위 밖 §4.)*

### F5. 조회 (History)
- **FR-11** 환자가 자기 예약 목록과 지난 진료 기록(진단·처방 포함)을 조회한다.
- **FR-12** 직원이 환자별 전체 진료 내역(예약·진료·처방)을 조회한다.

### F6. 참조 데이터 & 데모 시드
- **FR-13** 병원(1개)·진료과·의사·약 등 참조 데이터가 앱 구동에 필요한 만큼 존재한다(관리 화면 없이 시드로).
- **FR-14** 시연용 초기 시드 데이터(환자 몇 명, 진료과, 의사, 약)를 포함한다.

## 6. 비기능 요구사항 (Non-Functional Requirements)

- **NFR-1 (배포)** **공개 URL로 시연 가능하게 배포** — 아키텍처 결정(2026-07-13)에 따라 **프런트는 Vercel, 백엔드(FastAPI)는 Railway**에 올린다(브라우저는 Vercel 프런트를, 프런트는 Railway 백엔드를 호출). 초반에 배포 뼈대부터 세운다. *(당초 "Railway 단일" 문구를 아키텍처 단계에서 프런트 Vercel·백 Railway로 갱신. 세부: 아키텍처 스파인 운영 봉투.)*
- **NFR-2 (데이터 정합성)** 실제 **Supabase(PostgreSQL)** 사용, ERD의 **FK·CHECK 제약**(status 값, NOT NULL 등)을 준수한다.
- **NFR-3 (스택)** 프런트 **Next.js**, 백엔드 **FastAPI(Python)**. 브라우저는 Supabase를 직접 호출하지 않고 FastAPI만 호출한다.
- **NFR-4 (인증·보안)** 로그인은 범위 제외(역할 선택 대체). 단, **모든 테이블에 RLS를 활성화**하고 공개(anon) 키의 DB 직접 접근을 차단한다. 모든 DB 접근은 **FastAPI 백엔드(서버 측 키)** 를 통해서만 이뤄진다. 환자별 데이터 격리는 API 레벨 필터로 처리하며, 로그인이 없어 DB 레벨 사용자별 격리는 아님(확장 과제). **완료 정의:** 배포 전 **9개 테이블 RLS ON을 확인**한다(Supabase advisor로 점검). 현재 `db-design/schema.sql`엔 RLS 구문이 없으므로(A1 ⚠️) **RLS 활성화 마이그레이션을 배포 뼈대(NFR-1)와 함께 초기 산출물(P0)** 로 처리한다. *(구현 세부: `addendum.md` A1)*
- **NFR-5 (사용성)** 초급자·데모 관점 — **브라우저에서 전체 흐름을 눈으로 끝까지 확인** 가능해야 한다. 한국어 UI.

## 7. 가정 & 오픈 이슈 (Assumptions / Open Questions)

- `[ASSUMPTION]` 환자 신원 선택 = 목록에서 이름 선택. 실제 인증은 확장 과제(사용자 합의, 추후 변경 가능).
- `[ASSUMPTION]` 시드 데이터의 규모(환자/의사/약 개수)는 시연에 충분한 최소 수준으로 개발자 재량. 진료과당 의사 2명 이상 시드하면 자동 배정·충돌을 시연하기 좋다.
- `[결정]` 예약 **중복(가용성) 검증 포함** — (의사, 슬롯) 단위로 충돌 차단(FR-15). 단, **영업시간·근무표** 검증은 범위 밖(빈 슬롯 = 그 의사에게 겹치는 예약/walk-in이 없는 슬롯).
- `[결정]` **walk-in 포함**(FR-16) — 예약 없이 빈 의사에게 즉시 진료·기록. 예약과 동일한 (의사, 슬롯) 가용성을 점유.
- `[결정]` 슬롯 단위 = **30분 격자**. 예약 시각은 30분 단위로 선택, walk-in은 진료 시각을 그 슬롯으로 내림. 충돌은 **동일 (의사, 슬롯)** 기준(초 단위 정확 일치가 아님 — 그래야 walk-in이 예약을 실제로 막는다). 30분보다 긴 진료의 시간 겹침 계산은 확장.
- `[ASSUMPTION]` 실제 병원의 정량적 페인(대기시간·오류율 등)은 미조사 — 문제 정의는 강의 시나리오(환자 등록→진료→기록)에 근거한 과제 전제다.
