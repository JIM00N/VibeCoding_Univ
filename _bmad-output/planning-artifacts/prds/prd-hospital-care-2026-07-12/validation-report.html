Good

문서로서의 PRD는 최상급이다. "넓이보다 한 줄기 관통"이라는 명확한 테제가 성공 지표·역-지표·범위·FR 전체를 일관되게 관통하고, FR-15/16의 가용성·walk-in 충돌 규칙은 데모 스펙치고 이례적으로 정밀하며, 기존 db-design/ 스키마 참조가 실제 파일과 전부 일치한다. 루브릭 7개 차원이 모두 strong/adequate, critical·high 지적 0건 — 착수 차단 요소는 없다.

다만 "스키마가 PRD의 주장을 실제로 강제하는가"에서 그림이 바뀐다. 적대적·데이터모델 리뷰어가 공통으로 high 4건을 짚었다: ① NFR-4가 요구한 RLS가 schema.sql에 전혀 없어 이미 배포된 DB가 열려 있을 수 있고, ② 예약↔기록 1:1이 DB에서 미강제(appointment_id UNIQUE 부재), ③ 핵심 판매 포인트인 (의사,슬롯) 유일성이 두 테이블에 걸쳐 있어 DB 제약 0개·경쟁 조건에 노출, ④ P0 범위가 FR-6의 "항상 의사 배정"을 깨서 P0만 구현하면 성공지표 ①의 E2E가 성립하지 않는다. 넷 다 고칠 수 있고 일부는 PRD가 스스로 부록에 flag해 둔 것이라, 문서를 Excellent에서 Good으로 끌어내리되 "구현 전에 닫아야 할 목록"으로 다루면 된다.

먼저 처리할 것 — High 4건 (구현 착수 전 결정)

  1. P0 범위 ↔ FR-6 "항상 의사 배정" 충돌. P0는 자동배정을 빼는데 FR-6·성공지표 ①은 배정된 의사를 전제 → P0만으로 예약→기록 E2E가 막힌다. §4 P0 / FR-6·FR-9
  2. RLS 미구현. NFR-4/부록 A1은 9개 테이블 RLS ON을 요구하나 schema.sql에 RLS·POLICY 0건. 배포된 DB가 anon 키로 열려 있을 수 있음. NFR-4 / A1 / schema.sql
  3. 예약↔기록 1:1 미강제. medical_record.appointment_id에 UNIQUE가 없어 한 예약에 기록 여러 건·완료전이 중복 가능. FR-8·FR-9 / schema.sql:107
  4. (의사,슬롯) 유일성 DB 미강제. 충돌 소스가 appointment·medical_record 두 테이블 → 앱-레벨 검사뿐, 동시 요청 이중배정 위험. FR-15·FR-16 / A4

1. 의사결정 준비도

strong

핵심 결정들이 "고려사항"으로 묻히지 않고 결정으로 명시돼 있다 — 로그인 미구현(역할 선택 대체), 단일 병원 전제, 가용성 검증 포함, walk-in 포함이 모두 선언형이다. 트레이드오프도 정직하다: NFR-4/A1은 로그인이 없으면 진짜 격리가 불가능함을 스스로 인정하고 확장 과제로 넘기며, 역-지표(§2)는 "부가 화면을 넓히려다 핵심 완성이 지연되면 실패"라는 진짜 포기 대상을 지목한다. §7 오픈 이슈 대부분이 [결정]으로 닫혀 green-light 상태로 읽힌다.

2. 실질 대 겉치레

strong

겉치레가 거의 없다. 페르소나 3명(이수민/박서준/김민재)이 각자 UJ를 구동하고 — "로그인이 없으므로 의사도 직원 화면에서 기록을 작성한다"는 페르소나에서 직접 도출된 설계다. 강요된 차별화/혁신 섹션이 없고(과제 성격상 옳음), NFR도 제품 특정(ERD의 FK·CHECK 제약, deny-by-default 보안 자세)이라 보일러플레이트가 아니다. 유일한 경계선은 NFR-5의 "초급자·데모 관점" 형용사지만 "브라우저에서 끝까지 확인 가능"이라는 관찰 가능한 경계를 달고 있다.

3. 전략적 일관성

strong

명확한 테제가 있다: "정규화된 9개 엔티티 위에서 환자↔병원 핵심 흐름 한 줄기를 end-to-end 관통". FR-1~16 전부가 이 수직 슬라이스(접수→예약→진료→기록→조회)에 매핑되며 "쉬운 것부터"가 아니다. 성공지표 ①이 "전체 흐름 E2E 동작"을 핵심 지표로 못박아 활동량(DAU)이 아니라 관통 여부를 재고, 역-지표(카운터 지표)도 존재한다. P0/P1을 "제외가 아니라 구현 순서"로 프레이밍한 것이 문제 해결형 MVP 성격과 정확히 일치한다.

4. 완료 기준 명확성

strong

FR 대다수가 테스트 가능한 결과를 갖는다. FR-8은 완료 전이를 "예약에 진료 기록이 작성되면 status가 완료로 전이"로 트리거까지 못박았고, FR-15/16의 슬롯·walk-in 충돌 규칙은 데모 스펙치고 이례적으로 정밀하다. weasel word("gracefully/reasonable")는 FR 본문에 없다. 남는 것은 아래 문서 간 상충 한 건과 경미한 시드 하한이다.

medium

예약 시 담당 의사 배정 시점이 문서 간 상반되게 읽힘

§5 FR-6 / 부록 A3
FR-6·A4는 "예약에는 항상 담당 의사가 배정된다"인데 A3는 "doctor_id nullable(예약 시 미배정 허용)"이라 앱 정책과 정반대로 읽힌다. 계층(DB 컬럼 허용 vs 앱 정책 강제)이 분리 진술되지 않아 아키텍트가 재조정을 거쳐야 하고, 자칫 미배정 예약을 생성하는 경로를 열 수 있다.
Fix: A3에 "DB 컬럼은 nullable이나(스키마 안정성·walk-in 위해 유지), 앱 정책상 예약 생성 시 항상 채운다(FR-6·A4)" 한 줄을 추가해 두 계층을 명시 구분.
low

시드 수량 하한이 FR이 아닌 가정에만 존재

§5 FR-14 / §7
FR-14는 "시연에 충분한 최소 수준"으로만 두고, 자동배정·충돌 시연에 필요한 "진료과당 의사 2명 이상"은 §7 [ASSUMPTION]에만 있다. done 판정 기준이 FR 밖에 있다.
Fix: FR-14에 "충돌·자동배정 시연이 가능하도록 최소 1개 진료과에 의사 ≥2명 시드"처럼 검증 가능한 하한을 넣기.
low

NFR-5가 형용사에 기댐

§6 NFR-5
"초급자·데모 관점"은 경계가 아니라 태도. 뒤의 "눈으로 끝까지 확인 가능"과 §2 SM 체크리스트가 실질 기준을 살리므로 경미.
Fix: 관찰 가능한 후자를 수용 기준으로 앞세우고 형용사는 배경으로.

5. 범위 정직성

strong

제외(§4) 섹션이 실제로 일한다 — 로그인·병원 선택·참조 데이터 관리 화면·결제·재고·알림·모바일 등을 명시 배제해 "조용히 가정"될 여지를 없앤다. 부록 A1의 ⚠️(schema.sql에 RLS 없음)와 A3의 appointment_id UNIQUE 부재 고지는 스스로 파낸 자기 지적이며 실제 파일과 정확히 일치한다. 디스코핑이 조용하지 않고 명시적이라(영업시간·근무표·겹침 계산을 "범위 밖"으로 못박음) green-light 문서로서 부담이 없다.

6. 다운스트림 사용성

adequate

이 PRD는 스스로 bmad-architecture 입력임을 선언하므로 다운스트림이 유효하다. 도메인 명사가 본문·부록에서 일관되게 쓰이고 A3/A4에서 데이터 모델로 매핑돼 소스 추출이 대체로 깨끗하다. FR ID 1~16 전부 유일·교차참조 해소, UJ는 명명된 주인공을 갖는다. 다만 아키텍처 이관용 몇 가지 정비 여지가 있다.

7. 형태 적합성

strong

과제 형태(Hobby/solo)에 정확히 캘리브레이션 — 2페이지, 엔터프라이즈 페르소나·강요된 차별화 섹션 없음, rigor는 가볍되 실질 기준은 유지. 이해관계자가 환자+접수+의사로 복수이고 UX가 유의미하므로 명명된 주인공의 UJ가 load-bearing인데 실제로 그렇게 쓰였다. 본문(What)과 부록(How)을 깔끔히 분리해 chain-top 위생이 좋고, 준-브라운필드(기존 9개 테이블) 참조가 실제 파일과 전부 일치한다.

적대적 리뷰 (Adversarial)

review-adversarial.md

큰 지뢰(30분 슬롯 규칙·FR-6 자기모순·P0/P1 분리)는 이전 리뷰 반영으로 대부분 넘겼다. 그러나 핵심 판매 포인트인 "가용성 불변식"이 DB에서 전혀 강제되지 않는 앱-레벨 희망사항이고, P0 범위 정의가 FR-6·주요 여정과 정면충돌해 P0만 짜면 문서상 경로가 성립하지 않는다. 여기에 walk-in 미명세 구멍과 3일/1인 마감 리스크가 얹혀 "끝까지 관통" 목표가 P1 구간에서 조용히 깨질 여지가 크다. (critical 0 · high 2 · medium 7 · low 3)

high

P0 범위가 FR-6 "항상 의사 배정" 불변식을 깨고 FR-9를 막는다

§4 P0 / FR-6·FR-9 / schema:92,109
P0는 "자동배정을 뺀 기본 예약 생성"인데 FR-6은 "예약에는 항상 의사가 배정"이라 못 박았다. P0에서 의사를 비우면 appointment.doctor_id가 null로 남고(자동배정 없음), FR-9/진료기록은 medical_record.doctor_id NOT NULL을 요구 → P0 단독으로는 진료 기록을 못 쓴다. 성공지표 ①의 예약→배정→기록 E2E가 P0만으로 성립하지 않는다.
Fix: P0 정의에 "의사 미선택 예약은 직원이 기록 작성 전 수동 배정"을 명시하고 FR-6의 "항상 배정"을 "기록 시점까지 배정"으로 완화. 또는 최소 자동배정을 P0로 끌어올리기.
high

가용성 불변식이 DB에 전혀 강제되지 않는다 — "하나만"은 기도다

FR-15 / A4 / schema 전체
"(의사,슬롯)에 활성 예약/walk-in 하나만"은 appointment·medical_record 두 테이블에 걸쳐 있어 단일 부분 유니크 인덱스로 못 막고, 순수 앱-레벨 검사다(A4 인정). 전형적 TOCTOU 경쟁으로, 자동배정이 동시에 같은 의사를 집을 수 있다. DB 제약 0개 → 앱 버그·직접 쿼리 한 방에 조용히 깨진다. NFR-2의 "정합성"이 정작 예약 무결성엔 손도 못 댄다.
Fix: FR-15를 "동시 요청 없는 단일 세션 전제에서만 차단 보장"으로 격하 명시. 엄밀성을 원하면 union 뷰 위 EXCLUDE 제약 또는 점유 전용 slot_occupancy 단일화를 확장 항목으로 못박기.
medium

주요 사용자 여정이 P1 기능으로 서술돼 P0 구현자를 오도

UJ-1 step2, UJ-2 step3 vs §4
UJ-1의 "비워두면 자동 배정", UJ-2의 "배정된 담당 의사 확인"이 전부 P1(자동배정)에 의존 → P0부터 관통하라는 가드레일을 따르면 문서화된 유일한 여정이 P0에서 성립하지 않는다. "P0에서 사용자는 뭘 보는가" 시나리오가 없다.
Fix: UJ 각 스텝에 (P0)/(P1) 태그를 달거나 P0용 수동배정 경로를 병기.
medium

walk-in의 진료과 출처 미명세인데 컬럼은 NOT NULL

FR-16 / schema:110 / A4
FR-16은 "빈 의사에게 즉시 진료"만 말하고 예약이 없으니 진료과 선택 단계도 없다. 그런데 medical_record.hospital_department_id는 NOT NULL이고 "빈 의사"를 범위 지으려면 어느 진료과인지 먼저 정해져야 한다. 이 입력이 UJ-2/FR-16 어디에도 없다.
Fix: FR-16에 "walk-in 시 직원이 진료과를 먼저 선택하고 그 과의 빈 의사를 배정한다"를 추가.
medium

"대기로 처리"는 뒷받침 데이터 없는 dangling path

FR-16 말미 / §4 제외
walk-in 빈 의사 없을 때 "대기로 처리"라는데 §4는 "대기열"을 명시 제외했다. 대기 상태를 담을 엔티티도 완료 기준도 없어 검증 불가능하고, 개발자는 구현 대상이 없어 헤맨다.
Fix: "대기 처리"를 지우고 "빈 의사 없으면 거부 메시지로 종료"로 확정. 대기열이 필요하면 별도 FR·엔티티로 승격.
medium

"선택된 환자 데이터만 보인다"는 격리 언어가 실제 노출을 가림

FR-2 / 성공지표 ③ / A1-5
로그인이 없어 환자 목록이 전원의 이름·생년월일을 누구에게나 나열하고, API 필터는 클라이언트가 준 patient_id로 도는지라 방문자가 아무 환자나 골라 진단·처방을 전부 열람할 수 있다. 의도된 축소지만 FR-2 표현이 이를 격리처럼 오독하게 만든다(caveat이 A1엔 있으나 FR 본문엔 없음).
Fix: FR-2에 "이는 기밀 격리가 아니며 데모상 누구나 임의 환자를 선택·열람할 수 있음"을 한 줄 명시.
medium

예약:기록 1:1 미강제 + 완료 전이 트리거가 반쪽

FR-8·FR-9 / A3
appointment_id에 UNIQUE가 없어 한 예약에 기록 2건·재작성·중복 완료전이를 막는 가드가 없다. FR-8 완료 전이는 "예약에 기록 작성 시"인데 walk-in 기록은 appointment_id가 null이라 규칙 밖이고, 앱이 기록 저장 시 appointment.status='완료'를 손수 갱신해야 하는 이 "쓰기 부작용"이 어느 FR에도 없다.
Fix: "정상 예약 기록 저장 트랜잭션에서 status를 완료로 갱신"을 FR-8/9에 명시하고, '예약당 기록 1건' 앱 가드를 완료 기준에 포함.
medium

3일·1인·풀스택에 교차테이블 가용성 엔진+walk-in — P1 미착륙 위험

유형/마감 / §4 P1
오늘 07-13 기준 실질 3일. P1(교차테이블 충돌검사+자동배정+walk-in+재검사)은 버그가 몰리는 fiddly 구간인데, 성공지표 ①이 "진료 확정·의사 배정"을 핵심으로 걸어놔 P1이 빠지면 데모의 킬러 장면이 사라진다.
Fix: "P1 미완 시에도 성공으로 인정되는 최소 데모(수동 배정 E2E)"를 성공지표에 명시해 마감-품질 트레이드오프를 사전 합의.
low

과거·비경계 시각 예약 방지가 앱-레벨뿐 / 타임존 미고정

FR-6 / A4 / schema:93
reserved_at가 30분 경계인지·과거가 아닌지 강제하는 CHECK가 없어 앱 버그 하나면 03:17·어제 예약이 저장된다. 슬롯 계산 기준 타임존도 명시 고정이 안전.
Fix: "과거 슬롯 예약 거부"를 FR-6에, 슬롯 계산 기준 타임존(UTC 저장·슬롯 단위 비교)을 A4에 한 줄씩.

데이터 모델 리뷰 (FR ↔ 스키마 정합성)

review-datamodel.md

정규화 골격(9개 테이블)과 FR의 핵심 매핑은 대체로 정합하고(FR이 요구하는데 스키마에 없는 컬럼은 없음), "발생 진료과·의사를 medical_record가 자체 보관"과 "예약도 항상 의사 배정 → doctor_id NOT NULL" 개정은 스키마와 잘 맞는다. 그러나 ① 문서가 요구한 RLS가 schema.sql에 전무하고, ② appointment_id UNIQUE 부재로 예약:기록 1:1이 DB에서 깨질 수 있으며, ③ (의사,슬롯) 유일성은 슬롯 컬럼·제약이 0개라 전적으로 앱 로직에 의존한다 — 이 셋이 핵심 리스크. (높음 2 · 중간 1 · 낮음 4)

high

RLS 구문이 schema.sql에 전혀 없음 — NFR-4 보안 posture 미구현

NFR-4 / A1 / schema.sql 전체
NFR-4·A1은 9개 테이블 전부 enable row level security + anon 정책 미생성(deny-by-default)을 요구하지만 schema.sql에 RLS·POLICY가 0건이다. A2가 "Supabase 배포 완료"라 하므로 이 파일 그대로 배포됐다면 공개(anon) 키로 전 테이블 읽기/쓰기가 열려 있는 상태다. A1의 경고·메모로그 경고는 정확 — 현재는 문서상 선언만.
Fix: 배포용 마이그레이션에 9개 테이블 각각 alter table <t> enable row level security; + anon 허용 정책 미생성. 배포 프로젝트의 실제 RLS 상태를 Supabase advisor로 점검해 OFF면 즉시 적용.
high

medical_record.appointment_id UNIQUE 부재 → 1예약-1기록 미보장

FR-8·FR-9 / schema.sql:107 / erd.md:23
appointment_id ... on delete set null에 UNIQUE가 없어 ERD의 1:1이 DB에서 강제되지 않는다. 한 예약에 기록 2건 이상이면 FR-8 완료 전이와 FR-11/12 조회가 중복·모순된다. A3가 갭을 명시했으나 미해결.
Fix: walk-in(appointment_id NULL 다건 허용)을 깨지 않는 부분 유니크 인덱스: create unique index on medical_record(appointment_id) where appointment_id is not null;
medium

(의사,슬롯) 가용성 DB 안전망 전무 + 30분 정렬 CHECK 부재

FR-15·FR-16 / A4 / schema:93,111
슬롯을 표현하는 컬럼이 없고(원시 timestamptz만), reserved_at의 30분 정렬을 강제하는 CHECK가 없어 10:17 같은 값 저장 시 슬롯 키 비교가 깨진다. 충돌 소스가 두 테이블이라 단일 부분 유니크 인덱스로도 못 막아 동시 요청 이중배정이 가능하다.
Fix: appointment에 30분 정렬 CHECK(extract(minute from reserved_at) in (0,30) and extract(second from reserved_at)=0) + 예약/walk-in 검사·삽입을 한 트랜잭션으로. 엄밀 강제는 두 소스 합친 공용 슬롯 뷰 필요(확장).
low

"예약은 항상 의사 배정"은 앱 전용 + ON DELETE SET NULL로 뚫림

FR-6·FR-7 / schema:92 vs 109
컬럼이 nullable이라 DB가 불변식을 강제하지 못하고, 의사 삭제 시 appointment.doctor_id가 조용히 NULL이 되어 확정 예약이 의사 없이 남을 수 있다. 진료 기록은 RESTRICT라 보존되어 정책이 비대칭.
Fix: 의사를 물리 삭제 대상에서 제외(비활성 플래그)하거나 삭제 금지 운영정책 명시. P0의 null-의사 예약은 P1 활성화 전 반드시 배정으로 정리.
low

환자는 department 선택인데 예약/기록은 hospital_department_id 요구

FR-6·FR-13 / A3 / schema:91,110
예약/기록은 전역 department.id가 아니라 hospital_department.id를 참조한다. UI의 "진료과"를 raw department.id로 넣으면 FK 위반이고, 선택 진료과에 hospital_department 행이 없으면 삽입 실패한다.
Fix: 생성 시 (단일 hospital_id + department_id)로 hospital_department_id를 조회해 저장. 시드에서 hospital 1행 + 노출 진료과별 hospital_department 행 + 진료과당 의사 ≥2 보장.
low

walk-in도 빈 의사 없으면 거부해야 NOT NULL 삽입 에러 회피

FR-16 / schema:109-110
walk-in medical_record는 doctor_id·hospital_department_id 모두 NOT NULL. 빈 의사가 없으면 기록 생성 자체가 불가하므로 사용자에게 DB 에러가 노출되지 않도록 앱에서 먼저 거부해야 한다.
Fix: walk-in 플로우에서 빈 의사 없을 때 A4대로 거부(다른 시각 안내) 처리. hospital_department_id는 배정 의사의 소속에서 유도.

  • 스키마 대조(검증 완료): 부록 A1·A3의 스키마 서술(9개 테이블, appointment.status CHECK, medical_record.doctor_id NOT NULL, appointment.doctor_id nullable, appointment_id UNIQUE 부재, RLS 구문 부재)이 실제 db-design/schema.sql과 모두 일치 — 존재 코드 참조 정확.
  • 참조 경로: §8의 브리프 참조 ../../briefs/…는 정확히 해소되나, 데이터 참조 db-design/는 상대경로로 해소 안 됨(실제는 리포 루트). 루트 기준 경로로 통일 권장.
