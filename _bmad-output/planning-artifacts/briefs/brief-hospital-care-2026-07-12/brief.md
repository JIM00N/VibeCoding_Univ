# 제품 브리프: 병원 진료관리 풀스택 서비스 (hospital-care)

> 용도: **개발 나침반** — 목요일(2026-07-16) 마감 과제를 혼자 만드는 동안 "무엇을, 어디까지, 왜" 헷갈릴 때 돌아올 기준점.

## 요약 (Executive Summary)

병원의 **환자 접수 → 예약 → 의사 진료 → 진료 기록**으로 이어지는 현장 흐름을 하나의 웹 서비스로 관리한다. 환자는 직접 **예약을 잡고 자기 진료 기록을 조회**하고, 병원 직원(접수·의사)은 **환자 등록·예약 관리·진료 기록 작성**을 한 곳에서 처리한다.

데이터는 **환자·의사·진료기록**을 중심으로 병원·진료과·예약·처방·약까지 9개 테이블(ERD 설계 완료)로 정규화되어 있고, 이미 **Supabase(PostgreSQL)에 배포**되어 있다. 프런트는 **Next.js**, 백엔드는 **FastAPI**로 얹는다.

이 제품은 시장에 내놓는 상용 서비스가 아니라 **바이브 코딩 교육기관 과제**다. 따라서 "새로운 시장 해자"가 목표가 아니라, **정규화된 데이터 모델 위에서 환자↔병원 양측의 전체 흐름이 끝까지 동작하는 풀스택 앱을 완성**하는 것이 목표다.

## 문제 (The Problem)

병원 현장에서 접수·예약·진료·기록이 서로 다른 도구(종이 차트, 전화 예약, 분리된 장부)로 흩어지면:
- 직원은 "이 환자가 언제 왜 왔고 무슨 약을 받았는지"를 매번 다시 뒤진다.
- 환자는 자기 예약·과거 진료를 스스로 확인할 방법이 없어 전화로 물어본다.
- 진료 기록이 "그때 어느 병원/과에서 있었나" 같은 사실과 분리되어 이력이 왜곡되기 쉽다.

`[가정]` 과제 특성상 실제 병원의 정량적 페인(대기시간·오류율 등)은 조사 대상이 아니며, 위 문제 정의는 강의 시나리오(환자 등록→진료→기록)에 근거한다.

## 해결책 & 핵심 흐름 (The Solution)

하나의 서비스에서 아래 흐름이 끝까지 이어진다:

1. **환자 등록** — 직원이 신규 환자를 등록한다(데모 시드 포함).
2. **예약** — 환자가 병원·진료과를 골라 예약을 잡는다. (담당 의사는 진료 시 배정 가능 → 예약의 의사는 선택)
3. **진료** — 직원/의사가 예약을 확정하고 진료를 진행한다.
4. **진료 기록** — 의사가 진단·처방·소견을 기록으로 남긴다. 이 기록은 "발생 병원·진료과"를 스스로 보관해, 의사가 이직해도 과거 기록이 바뀌지 않는다.
5. **조회** — 환자는 자기 예약·진료 기록을, 직원은 환자별 진료 내역을 조회한다.

## 누구를 위한 것인가 (Who This Serves)

- **환자** — 예약을 스스로 잡고, 자기 진료 기록·다음 예약을 확인하고 싶다. 성공 = 전화 없이 앱에서 예약·조회가 된다.
- **병원 직원(접수·의사)** — 환자 등록, 예약 관리, 진료 기록 작성을 한 화면에서 빠르게. 성공 = 흩어진 장부 없이 한 곳에서 흐름이 돈다.

두 사용자 그룹이 있지만, 이번 범위에서는 **실제 로그인/인증을 구현하지 않는다.** 대신 **역할 선택(환자 / 직원)** 으로 해당 화면에 들어간다 — 인증 부담 없이 **전체 흐름의 작동 확인**에 집중하기 위한 의도적 선택. (실제 인증은 이후 확장 과제.)

## 범위 (Scope)

**1차 완성(MVP)에 포함 — 전부 필수:**
- **역할 선택** (환자 / 직원) — 실제 로그인 대신 역할을 골라 해당 화면으로
- 환자 등록 (직원 화면)
- 예약 잡기 (환자 화면) + 예약 관리(확정/취소·의사 배정, 직원 화면)
- 진료 기록 작성 (직원/의사 화면)
- 진료 기록 / 환자 조회 (환자: 본인 것 / 직원: 전체)
- 위를 받치는 참조 데이터(병원·진료과·의사·약)의 최소 관리 또는 시드

**명시적으로 제외 (이번엔 안 함):**
- 실제 로그인/인증 (역할 선택으로 대체)
- 결제/수납, 보험 청구
- 자재 재고 관리, 진단서 발급
- 알림(문자/푸시), 대기열
- 모바일 앱(Flutter) — 웹 우선
- 고도화된 보안/권한 세분화(감사 로그 등)

## 성공 기준 (Success Criteria)

- ✅ **전체 흐름이 끝까지 동작**: 환자 등록 → 예약 → 진료 확정 → 진료 기록 작성 → 환자/직원 조회가 UI에서 이어진다. *(사용자가 정의한 핵심 기준)*
- ✅ 9개 엔티티가 **ERD의 FK·제약대로** 생성/조회/수정된다 (실제 Supabase DB 사용).
- ✅ **역할 선택**(환자/직원)에 따라 다른 화면이 뜨고, 환자 화면은 선택한 환자의 데이터만 보인다.
- ✅ **Railway에 배포 완료** — 실제 URL로 접속·시연 가능. *(사용자 요구: 필수)*

## 기술 & 데이터 (Tech & Data)

- **DB:** PostgreSQL / **Supabase** — 프로젝트 `hospital-care`(`fphsxoweprztrekckzui`)에 스키마 배포 완료. 9개 테이블: hospital · department · hospital_department · doctor · patient · drug · appointment · medical_record · prescription. (ERD·SQL: `db-design/`)
- **백엔드:** FastAPI (Python)
- **프런트:** Next.js (React)
- **인증:** 이번 범위에서는 없음 — **역할 선택(환자/직원)** 으로 대체 (작동 확인 우선)
- **배포:** **Railway** (필수) — 실제 URL로 시연
- **핵심 설계 원칙:** 진료과는 전역 코드 + 병원진료과(N:M)로 중복 제거 / 진료기록이 발생 장소를 직접 보관해 이력 보존.

## 리스크 & 오픈 질문 (Risks / Open Questions)

- ⚠️ **로그인이 없어 실제 데이터 격리는 아님** — 역할 선택은 "작동 확인"용이라, 환자 화면의 "본인 데이터만"은 앱 레벨 필터일 뿐 진짜 보안이 아니다. Supabase RLS도 꺼져 있어 anon 키로 전 테이블 접근 가능 → **데모/과제 전제**임을 명확히 하고, 실제 인증·RLS는 확장 과제로 남긴다.
- ⚠️ **배포(Railway)가 필수** — 목요일까지 1인이 끝내야 하므로, **초반에 배포 뼈대부터 세워** 막판 배포 사고를 앞당겨 방지할 것. (인증을 뺀 만큼 부담은 줄었다.)
- ⏰ **일정** — 1인 개발, 마감 2026-07-16(목). 우선순위: **전체 흐름의 "한 줄기"부터 끝까지 관통**(역할 선택→예약→진료기록→조회) 후 나머지 화면 보강.
