02

10개 불변식 (AD)

각 카드 = 지켜야 할 규칙 + 그게 막는 발산. ● = 이미 확정된 것(ADOPTED).

경계 · 의존 · 계약
AD-1 · ADOPTED

3-tier 경계와 의존 방향

브라우저 → FastAPI → PostgreSQL 한 방향. 프런트는 DB 드라이버·시크릿을 import 안 함.
막음: 프런트가 Supabase 직접 호출·시크릿 번들 유출
AD-2

계층형 백엔드 · DB I/O는 db 계층만

routers=HTTP만, services=규칙+트랜잭션, db=유일한 커넥션. 상향 import 금지.
막음: 비즈로직이 라우터로 새거나 DB 접근이 흩어짐
AD-10

단일 API 계약

리소스당 응답모델 1개, 어디서나 같은 모양. 연관=FK id + 평평한 표시필드(doctor_name). 오류={detail}.
막음: 화면마다 JSON 모양이 달라 단일 프런트 클라이언트 불가
예약 · 가용성 · 상태
AD-3

슬롯 키 = 하나의 정규화 식

30분 격자 floor(UTC). 점유 판정은 SQL 충돌쿼리가 양 컬럼을 같은 식으로 정규화. Python to_slot()은 미러(UX용).
막음: walk-in이 예약을 못 막는 슬롯 계산 불일치
AD-4

가용성 검사 = 단일 함수, 한 트랜잭션

check_and_occupy(conn, …)가 호출자 트랜잭션을 받아 검사+삽입. 충돌원 = 예약(대기·확정) ∪ walk-in 기록.
막음: 3경로가 충돌검사 제각각 · 검사↔삽입 사이 경쟁
AD-5

status 전이는 예약 서비스만

기록은 확정 예약에만 생성 → 같은 tx에서 확정→완료. walk-in은 status 안 건드림. 예약당 기록 1건.
막음: 취소/미확정 예약에 기록이 붙는 불법 전이
이력 · 보안 · 데이터
AD-6

기록은 발생 시점 진료과·의사를 자체 저장

생성 시 값 복사(이력 불변). 예약기반=예약의 과, walk-in=배정의사 현재 소속. 라이브 조인 금지.
막음: 의사 소속 변경 시 과거 이력 왜곡
AD-7 · ADOPTED

보안 posture: RLS deny-by-default

9테이블 RLS ON, anon 정책 미생성. DB는 FastAPI의 DATABASE_URL로만(env 전용). 배포 후 advisor로 확인.
막음: anon 키로 DB 전체 노출 · 시크릿 번들 유출
AD-8 · ADOPTED

환자 스코핑 = API 필터(보안 아님)

환자 조회는 ?patient_id= 쿼리로만. 앱 레벨 필터임을 UI·문서에 명시(데모 전제).
막음: 엔드포인트마다 스코핑 제각각 · 전체환자 유출
AD-9

스키마 = 버전 마이그레이션만 · PK 정수

PK=bigint IDENTITY. P0 마이그레이션 3종(RLS·부분유니크·30분 CHECK)+시드. 시드는 OVERRIDING SYSTEM VALUE.
막음: 코드 가정과 라이브 DB 드리프트 · 시드 삽입 실패
03

가용성 모델 — 이 앱의 가장 미묘한 심장

한 (의사, 30분 슬롯)은 예약이든 walk-in이든 하나만. 충돌은 두 테이블을 합쳐서 본다.

① 예약 appointment

status ∈ 대기 · 확정인 행
슬롯 = floor(reserved_at, 30m)
∪ 같은
(doctor_id, slot)
으로 합집합

② walk-in medical_record

appointment_id가 null인 행
슬롯 = floor(visited_at, 30m)
규칙: 예약 생성 · 의사 변경 · walk-in 생성 — 세 경로 모두 삽입 직전 단 하나의 check_and_occupy()를 같은 트랜잭션에서 호출한다. 취소=슬롯 해제, 완료=과거라 무관.
정직한 경계: 단일 세션에서 차단 보장, 동시 요청 경쟁(TOCTOU)은 범위 밖(확장 과제).

05

빌드 순서 — 넓이보다 한 줄기 관통

P0를 배포 가능한 상태로 먼저 관통시키고, 그 위에 P1을 안전하게 얹는다.

  1. 배포 뼈대 + 마이그레이션P0
    Vercel·Railway 빈 앱 배포 + RLS(9테이블)·부분유니크·30분 CHECK 마이그레이션 + 시드. advisor로 RLS ON 확인.
  2. 환자 등록 · 목록P0
    직원 화면. routers/patients → services → db. 단일 API 계약(AD-10) 첫 적용.
  3. 예약 생성(의사 직접 선택) + 확정P0
    환자가 과·시각·의사 선택 → check_and_occupy로 슬롯 점유. 직원이 확정/취소.
  4. 진료 기록 + 처방 (완료 전이)P0
    확정 예약에만 기록 작성 → 같은 tx에서 완료. 진료과 자체 저장(AD-6).
  5. 조회 (환자/직원)P0
    환자=?patient_id= 필터, 직원=전체. ← 여기까지가 E2E 한 줄기.
  6. 가용성 강화 · 자동배정 · walk-inP1
    FR-15 충돌 검사 강화, FR-6 자동 의사 배정·빈 의사 없을 때 거부, FR-16 walk-in(빈 의사 헬퍼 공유), FR-7 재배정 재검사.
